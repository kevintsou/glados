# M3 實作計畫

## 介面（框架固定）

- **目的**：把已核准的 spec 和 case 轉成實作計畫，在動 code 之前先抓出問題。
- **層級**：模組
- **從哪裡進來**：
  - M2 完成。
  - P3 改版（介面或記憶體預算變了）。
  - C 變更處理判定「既有行為的 bug」：M2 補完 case 後，確認或更新計畫。
- **輸入**：模組 spec（有 H1 核准）、驗收合約與測試基準、架構文件。
- **輸出**：實作計畫（`artifacts/modules/<模組>/plan.md`），內容包括：
  - 每一步對應哪些 case。
  - 要改的檔案清單（會變成 M4 的可寫範圍）。
  - 預估的記憶體影響。
- **出口檢查**：計畫涵蓋所有 case、計畫審查、審查沒有未處置的阻擋項目、審查者與執行者不同。
- **出口關卡**：無。
- **失敗退回**：
  - 審查有阻擋項目 → 留在 M3 修計畫重審（計入輪數）。
  - 牽涉需求或架構的爭議 → 經 R 失敗分類退回 M1＋H1 或 P3＋G2。
- **迴圈上限**：待定。
- **可寫範圍**：可寫 `artifacts/modules/<模組>/plan.md` 與 `review/`（計畫審查的發現紀錄）；禁止改 FW source 與測試。
- **人怎麼參與**：不參與。
- **獨立性要求**：計畫審查的執行者和計畫的撰寫者不同（另一個 session，最好換模型）。

審查的放行規則見 [framework/04 §4.8](../framework/04_rules.md#48-審查放行)：依每一項發現的類型、處置與證據放行，不採「兩個 AI 達成共識」。

- **執行方式**：兩個都是無人在旁的單次執行。
