# P3 架構與介面

## 介面（框架固定）

- **目的**：依已核准的需求與 G1 核准的模組切分，定義模組對外介面及共享資源，讓每個模組能各自往下走；模組的 code 歸屬、切分與相依順序由 P2 決定。
- **層級**：專案
- **從哪裡進來**：
  - G1 核准之後。
  - C 變更處理判定「改模組介面或記憶體預算」，且 GC 已核准接受。
  - R 失敗分類判定「介面衝突」。
- **輸入**：
  - 差異分析（模組切分有 G1 核准，且仍有效）。
  - 目前採用的來源快照與 CR 修訂紀錄（有修訂時才有）：G1 建立的基準及 GC 已接受的後續需求版本；逐項核對版本與核准依據，見 [framework/03 §3.2](../framework/03_artifacts.md#32-編號版本與-hash)。
  - 基線報告、專案設定（記憶體預算、衝突熱點）。
  - 重新進入時附 R 判定紀錄或 GC 核准的影響報告。
- **輸出**：架構文件（`artifacts/arch.md`），至少包括：
  - 介面合約：每個模組的對外介面，用編號條目寫，對應目前採用的需求來源或差異分析條目及所屬模組，讓 M3、M4 可以引用、過期時可以追蹤。
  - 記憶體預算分配。
  - 錯誤碼表。
  - boot flow 的變更。
- **出口檢查**：模組介面與預算已定。
- **出口關卡**：G2 架構審查。
- **失敗退回**：差異分析的 code 歸屬、模組切分或相依順序有誤 → 由 R 判定輸入不足，退回 P2 修正並重開 G1；需要改已核准的範圍、需求或專案設定 → 交 C＋GC。具體界線見 [framework/02 §2.6](../framework/02_workflow.md#26-模組之間)。
- **迴圈上限**：不設（架構審查會議有人在場）。
- **可寫範圍**：可寫 `artifacts/arch.md`；不能代改範圍清單、差異分析、CR 修訂紀錄、來源快照或專案設定；禁止改 FW source。
- **人怎麼參與**：與 AI 一起做（架構審查會議）。
- **獨立性要求**：無。

**改版時的影響**：依條目追溯，依賴改動介面或記憶體預算的模組從 M3 重走；不因此讓所有模組重跑。一般過期規則見 [framework/04 §4.4](../framework/04_rules.md#44-過期與重新進入)。

G1 核准的是需求基準與模組切分；P3 形成的架構文件另由 G2 核准。P3 首次細化架構，或依 R 在既有基準內修正介面，不因已通過 G1 就自動成為需求變更；涉及改模組切分、需求或專案設定時，仍須走上述原產出節點及關卡，不能只靠 G2 接受。
