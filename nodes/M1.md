# M1 需求與驗收

## 介面（框架固定）

- **目的**：把這個模組的需求寫成有編號、可驗證、沒有待確認事項的 spec 條目，並在同一場討論定出「什麼叫做完」（驗收合約）。v0.9 起原本 M2 的驗收合約移到這一站，H1、H2 合併成一次 H。
- **層級**：模組
- **由誰做**：外部互動。
- **從哪裡進來**：
  - P2 規劃完成、G1 核准（第一次）。
  - C＋GC 接受「改既有模組的需求」。
  - 人指定重做（例如 spec 有缺口或矛盾、驗收標準要改）。
- **輸入**：
  - 架構文件中這個模組的介面與預算。
  - 差異分析中這個模組的範圍項目，以及相關的來源快照與 CR 修訂紀錄。
  - 專案設定的觀察手段、製造錯誤的手段、既有測試項目。
  - 知識庫。
- **輸出**：
  - 模組 spec（`artifacts/modules/<模組>/spec.md`）：有編號的條目（B1、B2…），每一條引用來源（CR、spec 頁、CR 修訂紀錄、知識庫）。不能寫成一整段敘述。
  - 驗收合約（`artifacts/modules/<模組>/contract.md`）：每一條對到 spec 條目，寫明預期行為、用什麼訊號或方式判定、必要的好、壞、邊界情境。要用到另一支程式這版才改的功能（例如 bootcode 的 case 需要新 burner 才寫得出要讀的資料）的 case，標「延到 P4」並寫出依賴哪個功能（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。
  - 待確認事項清單（`artifacts/modules/<模組>/tbd.md`）：要等客戶、SOC、HW 回答的問題。
- **擋關檢查**：無（內容由 H 核准）。
- **收件檢查**：見 [framework/05 §5.5](../framework/05_checks.md#55-收件檢查) 的 M1 列。
- **出口關卡**：H 模組需求核准（spec 條目與驗收合約）。
- **失敗時**：來源不足或互相衝突 → 登記待確認事項，轉為「等外部回覆」；專案設定「寫進 Jira」允許時由工具寫進 Jira，不允許時由人轉問，答案記回待確認事項清單。
- **可寫範圍**：可寫 `artifacts/modules/<模組>/spec.md`、`contract.md`、`tbd.md` 與交接說明；禁止改 FW source 與測試。

**驗收合約的保護**：H 核准後，刪除必要情境、放寬預期、改變判定方式或必要覆蓋，一定要回 M1 重新經 H。在已核准的合約內補 case 或修正測試實作，由 M2 處理，不重開 H。

## 實作（待展開）

- **執行者**：人＋agent。
- **工具**：bct-grill-me（一次問一個問題）、bct-to-spec（把討論整理成有編號的條目）、bootcode-qa、pyconvert。
- **待展開議題**：
  - 回答問題的人如果參與過該專案的傳統開發，答案要標註來源（E39 的特別要求）。
  - E39 的 Epic 底下約 200 張 sub-task 能不能當驗收合約的來源（E39 待決）。
