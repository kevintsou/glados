# M1 需求釐清

## 介面（框架固定）

- **目的**：把這個模組的需求寫成有編號、可驗證、沒有待確認事項的 spec 條目。
- **層級**：模組
- **從哪裡進來**：
  - P3 展開（第一次）。
  - C 變更處理判定「改既有模組的需求」。
  - R 失敗分類判定「spec 缺口或矛盾」。
- **輸入**：
  - 架構文件（有 G2 核准）。
  - 差異分析中這個模組的範圍項目，以及需求基準裡對應的 CR 與 spec 頁：來源快照加上 CR 修訂紀錄，有修訂的以修訂後的內容為準（專案不寫回 Jira 時，快照裡只有修訂前的內容）。
  - 知識庫（環境清單固定的版本）。
- **輸出**：
  - 模組 spec（`artifacts/modules/<模組>/spec.md`）：有編號的條目（B1、B2…），每一條引用來源（CR、spec 頁、CR 修訂紀錄、知識庫）。不能寫成一整段敘述。
  - 待確認事項清單（`artifacts/modules/<模組>/tbd.md`）：要等客戶、SOC、HW 回答的問題。
- **出口檢查**：spec 條目有編號且有來源、沒有未解決的待確認事項。
- **出口關卡**：H1 需求核准。重走時只審差異與受影響範圍。
- **失敗退回**：來源不足或互相衝突 → 登記待確認事項，節點轉為「等待外部回覆」；專案設定「寫進 Jira」允許時由工具寫進 Jira，不允許時由人轉問，答案記回待確認事項清單。答案回來後開新 session 從檔案接續。
- **迴圈上限**：M1a 2 輪；M1b 不設（人在場）。
- **可寫範圍**：可寫 `artifacts/modules/<模組>/spec.md`、`tbd.md`；禁止改 FW source 與測試。
- **人怎麼參與**：分兩段。M1a 由 AI 草擬，人不參與；M1b 由人和 AI 一起討論定案。
- **獨立性要求**：無。

## 實作（待展開）

- **執行者**：M1a 是 AI；M1b 是人＋AI。
- **執行方式**：M1a 無人在旁執行；M1b 互動式 session，用 grill-me 的方式一次問一個問題。
- **工具**：bootcode-qa、pyconvert、grill-me。
- **待展開議題**：
  - grill-me 的本體不在 openBCT 或 bct_knowledge_base 裡（openBCT 的 write-jira-desc 有引用它），來源與版本待確認。
  - 互動式節點不能用 Stop hook 強制交出交接清單，改用收尾指令（見 [impl/ai_node_execution.md](../impl/ai_node_execution.md)）。
  - M1b 回答問題的人如果參與過該專案的傳統開發，答案要標註來源（E39 的特別要求）。
