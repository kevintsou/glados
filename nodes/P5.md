# P5 全量驗收

## 介面（框架固定）

- **目的**：證明其他功能沒有被改壞，整版可以交付。
- **層級**：專案
- **由誰做**：全量驗收的執行是工具步驟，由串接層執行；差異清單與安全審查是外部互動，由人開 agent 照 skill 完成，兩件事分兩次開工（[framework/04 §4.2](../framework/04_rules.md#42-兩種執行方式)）。
- **從哪裡進來**：P4 完成之後。
- **輸入**：P4 的整合 branch 與 boot flow 報告、差異分析的 regression 範圍、基線報告（判斷 FAIL 是新改動造成的，還是基底原本就是這樣；基線待處理清單依 GB 的處置判讀）、所有模組的測試基準、範圍清單（判斷哪些 case 因為功能被移除而可以拿掉）。
- **輸出**：全量驗收報告（`artifacts/acceptance/`）：regression 報告（綁定 image hash 與測試基準）、靜態分析報告、授權掃描報告、安全審查報告、交付版本與驗證版本差異清單（專案設定標的每一項差異，例如測試專用旗標、ASIC 與 FPGA 的差別，寫明驗證版本的結果為什麼能代表交付版本；說明不了的登記為驗證缺口，[framework/09 §9.3](../framework/09_build_configurations.md#93-規劃時不能忽略的事)）。
- **擋關檢查**：必要 case 全部 PASS、測試標準沒被放寬、靜態分析、授權掃描、審查沒有未處置的阻擋項目（安全審查）、交付版本與驗證版本差異清單每一項都有說明或已登記為驗證缺口。
- **出口關卡**：G3 最終交付核准（綁定整合 branch 的 commit 與交付版本的 image hash）。mask ROM 專案交付就是 tapeout，G3 的審查標準要比一般 release 更嚴。
- **失敗時**：交給人，先找出對應的模組，再決定回該模組的哪一站。
- **可寫範圍**：可寫 `artifacts/acceptance/`；禁止改 FW source 與測試。

安全審查的執行者和各模組 M4 的執行者不同。

## 實作（待展開）

- **執行者**：工具執行驗收；差異清單由人開的 agent 照差異清單 skill 寫；安全審查由人開的 agent 照安全審查 skill 完成，和各模組 M4、寫差異清單的那次都是不同 session，並一起審差異清單。
- **工具**：openBCT、bct-p5-variants（差異清單）、bct-p5-security（安全審查）、ci-owner（Coverity／cppcheck／Black Duck）、corvia-code-review。
- **待展開議題**：
  - openBCT 的 `RunResult.passed` 允許 SKIP（`core/models.py`）。放行要用「必要 case 全部 PASS」自己判斷，不能直接用它。
  - 靜態分析的必要規則清單內容（寫在專案設定，[framework/07](../framework/07_project_profile.md)）。
