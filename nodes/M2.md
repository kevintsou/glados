# M2 測試實作

## 介面（框架固定）

- **目的**：依 H 核准的驗收合約寫出 case，並證明 case 真的抓得到問題，在寫 code 之前把正確答案鎖住。
- **層級**：模組
- **由誰做**：寫 case 與測試審查是外部互動，由人開 agent 照 skill 完成，兩件事分兩次開工（審查是另一個 session）；判別能力是工具步驟，由串接層在提交後執行（[framework/04 §4.2](../framework/04_rules.md#42-兩種執行方式)）。
- **從哪裡進來**：
  - M1 完成（有 H 核准）。
  - C＋GC 判定「既有行為的 bug」：先補一個能重現 bug 的 case。
  - 人指定重做（例如判定是測試寫錯）。
- **輸入**：
  - 驗收合約與模組 spec（有 H 核准）。
  - 目前的 image（模組 branch 目前 build 出來的；第一次進來時就是基線報告的基底 image），用來取得判別能力證據。
  - 專案設定的觀察手段、製造錯誤的手段。
- **輸出**：
  - 測試實作（放在專案設定的測試框架位置）：case、輸入資料、執行腳本；每個 case 引用它驗證的 spec 條目。
  - 判別能力證據（見下方）。
  - 測試審查報告（`artifacts/modules/<模組>/review/`）。
  - 測試基準：M2 完成時，**由串接層**記下合約與測試實作的內容 hash，節點不能自己建。
- **擋關檢查**：只寫在允許範圍內、每個必要情境都有 case、判別能力、審查沒有未處置的阻擋項目（另一個 session 審查 case 是否真的落實合約）。
- **出口關卡**：無。
- **失敗時**：
  - spec 條目沒辦法轉成可驗證的 case、需要改驗收合約 → 交給人，通常回 M1。
  - 平台觸發不了或觀察不到 → 登記驗證缺口，交給人決定補哪種驗證手段。
- **可寫範圍**：可寫測試框架位置的測試實作與 `artifacts/modules/<模組>/review/`；禁止改 FW source 與驗收合約。

- AI 可以在已核准的合約內新增 case 或修正測試實作；刪除必要情境、放寬預期、改變判定方式或必要覆蓋，一定要回 M1 重新經 H。
- 測試審查要確認 case 真的落實了合約。例如「HMAC 錯誤必須拒絕 ID page」，不能只用「印出錯誤訊息」當作成功的證據。

### 判別能力：證明 case 真的抓得到問題

| 情況 | 必要的證據 |
| :---- | :---- |
| 新功能或 bug 修正 | 在還沒實作或修正這個行為的 image 上，因為目標原因 FAIL；實作後的 PASS 由 M5 確認 |
| 既有功能或 regression | 正常版本 PASS；再用錯誤注入或受控修改，證明 case 能抓到違反需求的行為 |
| 平台觸發不了或觀察不到 | 登記驗證缺口與受影響的需求，由人決定補哪種驗證手段；補足之前不能算 PASS |

- 連不上 FPGA、下載 image 失敗等屬於環境錯誤，不能當作成功重現了目標 bug。
- 錯誤注入或受控修改要用隔離的測試版本，保留修改內容、image hash 與結果證據，不能合入交付版本。
- 選試點模組之前，至少要確認一條需求能在現有平台上被觸發、觀察，而且結果穩定。

## 實作（待展開）

- **執行者**：人開的 agent 照測試實作 skill 寫 case；另一次開工由審查 skill 審查；判別能力由串接層的工具執行。
- **工具**：write-openbct-test、write-jira-desc（都在 openBCT 的 `.agents/skills/`）、openBCT。write-jira-desc 會寫進 Jira，受專案設定「寫進 Jira」限制（E39 不寫）。
- **待展開議題**：
  - 各專案可用的錯誤注入與受控修改手段（E39：`VUC_InjectError`、`VUC_OcpRecoveryErrorInject`、`phal_update_boot_inject_error`）。
  - openBCT 的報告目前沒有 image hash（見 [M5](M5.md)）。
