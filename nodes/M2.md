# M2 驗收定義

## 介面（框架固定）

- **目的**：依已核准的 spec 定出「什麼叫做完」，在寫 code 之前先把正確答案鎖住。
- **層級**：模組
- **從哪裡進來**：
  - M1 完成（有 H1 核准）。
  - C 變更分析判定「既有行為的 bug」：先補一個能重現 bug 的 case。
  - R 失敗分類判定「測試實作錯」或「驗收標準要改」。
- **輸入**：
  - 模組 spec（已通過且有效，有 H1 核准）。
  - 目前的 image（用來取得判別能力證據）。
  - 專案設定的觀察手段、製造錯誤的手段、既有測試項目。
- **輸出**：
  - 驗收合約：對應 spec 條目、預期行為、用什麼訊號或方式判定、必要的好壞情境與邊界覆蓋。
  - 驗收清單：每一項的執行結果一開始都是「未執行」。
  - 測試實作：case、輸入資料、執行腳本、和合約的對照。
  - 判別能力證據（見下方）。
  - 測試基準：**由串接層**在核對證據後建立新版，節點不能自己建。
- **出口檢查**：每個必要情境都有 case、判別能力、測試落實驗收合約、審查者與執行者不同；合約新增或變更時加上必要核准齊全。
- **出口關卡**：H2 驗收合約核准，只在合約新增或變更時需要。在已核准的合約內補 case 不重開 H2。
- **失敗退回**：
  - spec 條目沒辦法轉成可驗證的 case → M1。
  - 平台觸發不了或觀察不到 → 登記驗證缺口，交給人決定補哪種驗證手段。
- **迴圈上限**：2 輪。
- **可寫範圍**：可寫 `tests/`、`cases/`、驗收清單；合約變更要 H2；禁止改 `src/`；不能改或移動測試基準。
- **人怎麼參與**：只在 H2。
- **獨立性要求**：「測試落實驗收合約」的審查者和 M2 的執行者不同。

### 驗收合約和測試實作分開管理

| 產出 | 內容 | 怎麼放行 |
| :---- | :---- | :---- |
| 驗收合約 | 對應 spec 條目、預期行為、可以證明行為的判定訊號或方式、必要的好壞情境與邊界覆蓋 | H2 人工核准，綁定版本與內容 hash |
| 測試實作 | case、輸入資料、執行腳本、合約對照與判別能力證據 | 獨立審查＋工具驗證，由串接層放行 |

- AI 可以在已核准的合約內新增 case 或修正測試實作；但刪除必要情境、放寬預期、改變判定方式或必要覆蓋，一定要回 H2。需求本身有缺口或矛盾，則先回 M1。
- 獨立審查要確認 case 真的落實了合約。例如「HMAC 錯誤必須拒絕 ID page」，不能只用「印出錯誤訊息」當作成功的證據。
- 驗收清單的執行結果由工具產生。還沒執行記「未執行」；不能把未執行、環境錯誤或驗證缺口混成行為上的 FAIL 或 PASS。
- 人工核准的驗收合約受保護；通過檢查的測試集合由串接層建立新版測試基準，綁定合約、測試內容 hash 與審查證據。M4 沒有權限修改或移動它。

### 判別能力：證明 case 真的抓得到問題

不是一律要求「在還沒實作的 image 上 FAIL」，依情況分三種：

| 情況 | 必要的證據 |
| :---- | :---- |
| 新功能或 bug 修正 | 在還沒實作或修正這個行為的 image 上，因為目標原因 FAIL；實作後的 PASS 由 M5 確認 |
| 既有功能或 regression | 正常版本 PASS；再用錯誤注入或受控修改，證明 case 能抓到違反需求的行為 |
| 平台觸發不了或觀察不到 | 登記驗證缺口與受影響的需求，由人決定補哪種驗證手段；補足之前不能算 PASS，也不能說已完成驗證 |

- M2 在實作前要取得「目標 FAIL」或「既有功能的判別能力」證據；實作後的 PASS 由 M5 確認，不是 M2 的出口條件。
- 連不上 FPGA、下載 image 失敗等屬於環境錯誤，不能當作成功重現了目標 bug。
- 錯誤注入或受控修改要用隔離的測試版本，保留修改內容、image hash 與結果證據，不能合入交付版本。
- 選試點模組之前，至少要確認一條需求能在現有平台上被觸發、觀察，而且結果穩定。
