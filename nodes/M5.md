# M5 驗證

## 介面（框架固定）

- **目的**：證明 M4 產出的 image 符合驗收合約。
- **層級**：模組
- **從哪裡進來**：M4 完成。
- **輸入**：M4 build 證據裡的 image（hash）、測試基準、驗收合約、專案設定的驗證環境。
- **輸出**：
  - 驗證報告（`artifacts/modules/<模組>/verification/`）：每條 case 的結果（PASS／FAIL／未執行／環境錯誤／驗證缺口），綁定 image hash、測試集合的版本與 hash、驗證環境的版本或設定 hash、驗收合約版本、執行編號、原始 log 的 hash。
  - 驗收清單的執行結果。
- **出口檢查**：執行測試、必要 case 全部 PASS、證據對應目前版本。
- **出口關卡**：無。
- **失敗退回**：一律交給 R 失敗分類。
  - 必要 case FAIL → 由 R 判斷是 code 錯、測試實作錯，還是 spec 有缺口。
  - 環境錯誤 → R 交給人處理環境。
  - **拿不到「測試時跑的是哪個 image」的證明 → 登記驗證缺口，不能算 PASS**；R 交給人決定補哪種驗證手段。
- **迴圈上限**：待定（code 錯退回 M4 時，計入 M4 的輪數）。
- **可寫範圍**：可寫 `artifacts/modules/<模組>/verification/`；禁止改 FW source 與測試。
- **人怎麼參與**：不參與。
- **獨立性要求**：無。

## 實作（待展開）

- **執行者**：工具＋AI 判讀 log。
- **執行方式**：純程式跑測試；AI 判讀 log。
- **工具**：remote-ice、openBCT、bootcode-qa（log 判讀）、logic-analyzer（實體訊號）、pps-log-verify（以已知通過的 log 當標準比對）。
- **待展開議題**（2026-10-07 核對 openBCT main `d995897`）：
  - **image 載入和跑測試分屬兩個工具**：把 image 載進 FPGA 目前靠 bct_knowledge_base 的 remote-ice（DS-5 的 `debugger.exe`）；openBCT 的 `ArmICE` 還是 stub（`lab/ice.py`）。兩者之間沒有共同的紀錄，證明不了「openBCT 跑測試時，FPGA 上是哪個 image」。展開時要決定由誰把「載入、跑測試、綁定 image hash」做成同一次執行。
  - **設備互斥**：openBCT 的 `DeviceLease` 是本機的檔案鎖，以 device path（COM 埠、PhysicalDrive）為單位，管不到 FPGA 與 ICE，也不跨機器；remote-ice 載入時不會擋住別人同時用 openBCT。
  - **報告缺 hash**：openBCT 的 `summary.json` 只有執行編號（`run_id`）、時間、各 test 的結果與訊息，沒有 image、測試集合、驗證環境的 hash。
  - **通過的定義不同**：openBCT 的 `RunResult.passed` 允許 SKIP；放行要用「必要 case 全部 PASS」自己判斷。
