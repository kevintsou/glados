# M5 驗證

## 介面（框架固定）

- **目的**：證明 M4 產出的 image 符合驗收合約。
- **層級**：模組
- **由誰做**：工具步驟，由串接層執行；M4 提交通過後可以自動接續（[framework/04 §4.2](../framework/04_rules.md#42-兩種執行方式)）。
- **從哪裡進來**：M4 完成。
- **輸入**：M4 build 證據裡的 image（hash）、測試實作與測試基準、驗收合約、專案設定的驗證環境。
- **輸出**：驗證報告（`artifacts/modules/<模組>/verification/`）：每條 case 的結果（PASS／FAIL／未執行／環境錯誤／驗證缺口），綁定 image hash、測試基準、原始 log。測試需要另一支程式時（bootcode 的測試用到 burner，或 burner 跑在 bootcode 上），也記下那一支的 image hash。另一支程式用固定的一個版本（P1 基線用的那一版），不跟著它的開發變動，讓問題隔離在被測的模組；完整版本的組合留到 P4 驗（2026-10-28 使用者決定，[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。
- **擋關檢查**：必要 case 在合約標的每個適用 build 設定上全部 PASS，結果按設定分開記、各自綁那個設定的 image hash（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。驗收合約標了「延到 P4」的 case 不在 M5 跑，記「未執行（延到 P4）」，不擋 M5，由 P4 驗（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。
- **出口關卡**：無。
- **失敗時**：
  - 必要 case FAIL → 回 M4 重做，計入 M4 的輪數；判斷可能是測試寫錯或 spec 有缺口時，交給人。
  - 環境錯誤 → 交給人處理環境。
  - **拿不到「測試時跑的是哪個 image」的證明 → 登記驗證缺口，不能算 PASS**，交給人決定補哪種驗證手段。
- **可寫範圍**：可寫 `artifacts/modules/<模組>/verification/`；禁止改 FW source 與測試。

## 實作（待展開）

- **執行者**：工具。需要判讀 log 時（例如找 FAIL 的原因），由人開 agent 判讀，通常併入下一次 M4；判讀不影響是否通過。
- **工具**：remote-ice、openBCT、bootcode-qa（log 判讀）、logic-analyzer（實體訊號）、pps-log-verify（以已知通過的 log 當標準比對）。
- **待展開議題**（2026-10-07 核對 openBCT main `d995897`）：
  - **image 載入和跑測試分屬兩個工具**：把 image 載進 FPGA 目前靠 bct_knowledge_base 的 remote-ice；openBCT 的 `ArmICE` 還是 stub（`lab/ice.py`）。兩者之間沒有共同的紀錄，證明不了「openBCT 跑測試時，FPGA 上是哪個 image」。展開時要決定由誰把「載入、跑測試、綁定 image hash」做成同一次執行。
  - **設備互斥**：openBCT 的 `DeviceLease` 是本機的檔案鎖，管不到 FPGA 與 ICE，也不跨機器。
  - **報告缺 hash**：openBCT 的 `summary.json` 沒有 image 與測試集合的 hash。
  - **通過的定義不同**：openBCT 的 `RunResult.passed` 允許 SKIP；放行要用「必要 case 全部 PASS」自己判斷。
