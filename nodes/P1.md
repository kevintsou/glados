# P1 基底與基線建立

## 介面（框架固定）

- **目的**：從 G0 核准的起點與生成配方，建立這個專案可以用的 code base（基底），再量出對照基準。之後出現 FAIL 時，才分得出是新改動造成的，還是基底原本就是這樣。
- **層級**：專案
- **從哪裡進來**：
  - G0 核准之後。
  - C 變更處理判定「改基底、平台或 toolchain」（包括生成配方或外部來源換版），P0 重走之後（所有證據過期）。
  - GB 不核准，或 GB 判定某個基線 FAIL 是移植問題。
  - P2 退回：基線缺既有功能的測試結果，regression 範圍定不出來。
- **輸入**：
  - 專案說明、範圍清單、專案設定、環境清單（都已通過且有效，有 G0 核准）。專案設定的「起點與生成配方」決定要怎麼建立基底（[framework/07](../framework/07_project_profile.md)）；範圍清單裡的既有功能（標成保留、修改、移除的項目）就是基線要跑的對象。
  - 生成配方列的外部來源快照（例如 register、HW spec），由工具在 P0 依專案設定產生，P1 只讀快照，不讀原始位置。
- **做什麼**（依序）：
  1. **起點檢查**：起點 commit 上，必要 build 設定對應的設定都 build 得過。只確認起點可用，不當成基線。起點是已發佈或已驗證的版本（依據記在專案說明），P1 不重跑它的功能測試。
  2. **機械替換**（有生成配方時）：串接層依生成配方執行確定性工具（例如 bcgen 或 script），把外部來源的內容換進 code、建立新 IC 的目錄與 build 設定，commit 成一個獨立的 commit。只寫專案設定列的生成區；同一份配方重跑必須得到相同的結果。
  3. **移植**（有生成配方時）：機械替換做不到的部分由 AI 修改，例如 register 改變後受影響的 HAL 與初始化。只改專案設定列的移植範圍；每處修改都要對到生成配方的項目、register 差異或 HW spec 的出處，記在移植項目清單。和機械替換的 commit 分開。
  4. **移植審查**（有移植修改時）：另一個執行者審查移植的 diff，核對修改有依據、沒有超出範圍、沒有關掉功能或放寬 build 設定來讓結果通過。
  5. **量基線**：在基底上 build 所有必要設定，在驗證平台跑範圍清單列的既有功能。保留的既有功能 FAIL 時不能略過，列成待處理清單交 GB 逐項決定。
  - 沒有生成配方的專案（例如同一顆 IC 的改版），跳過第 2–4 步，基底就是起點 commit。
- **輸出**：
  - 基底 commit：在專案層工作 branch 上，機械替換的 commit 加上移植的 commit；沒有生成配方時就是起點 commit。GB 核准後，模組與整合 branch 都從它開出（[framework/03 §3.12](../framework/03_artifacts.md#312-存放位置與寫入權限)）。
  - 基底建立紀錄（`artifacts/base/`）：生成紀錄（配方版本、工具與版本、輸入 hash、機械替換 commit、重跑比對結果）、移植項目清單、移植審查報告與發現紀錄。
  - 基線報告（`artifacts/baseline/`）：
    - G0 核准的每個必要 build 設定的結果、image hash、記憶體用量；另核對盤點清單與專案設定的處置，核准的排除項目不計為 PASS。
    - 既有功能的測試結果與 golden log：綁定 image hash、測試集合與驗證環境的版本與 hash。
    - 待處理清單：保留的既有功能在基底上 FAIL 的項目，附證據。
- **出口檢查**：起點可 build、機械替換可重現、只寫在允許範圍內、移植修改都有依據、審查沒有未處置的阻擋項目、審查者與執行者不同、build 零警告（所有必要 build 設定）、既有功能已量測、證據對應目前版本（[framework/05](../framework/05_checks.md)）。
- **出口關卡**：GB 基底核准（核准基底 commit 的確切版本、移植審查結果與基線報告；逐項決定待處理清單，[framework/02 §2.4](../framework/02_workflow.md#24-人工關卡)）。
- **GB 對待處理清單的決定**：

  | 決定 | 之後怎麼走 |
  | :---- | :---- |
  | 移植問題 | 退回 P1 第 3 步修正，計入移植輪數；修正後重量基線、重開 GB |
  | 新 IC 本來就不同，這版要改 | 回 P0 把這項既有功能改標「修改」，重開 G0 只審差異，之後交給模組處理；基線保留這個 FAIL 結果，不必重量 |
  | 接受，這版不處理 | 記錄理由；P5 把它當成基底原本的狀態 |

- **失敗退回**：
  - 生成配方不完整或有誤（外部來源缺版本、register 對照錯、生成區或移植範圍不夠），或 build 設定漏列、仍待確認、盤點不完整 → R 判定輸入不足，退回 P0（重開 G0 只審差異）。移植需要改移植範圍以外的檔案也一樣，不能自行擴大範圍。
  - 機械替換的工具出錯或重跑結果不同 → 交給人。
  - 起點本身 build 不過、環境或工具問題 → 交給人（可能要回 P0 換起點）。
  - P1 不自行把失敗的必要設定改成排除。
- **迴圈上限**：移植 3 輪（build 不過或量測發現移植錯誤，在第 3 步重做）；移植審查的阻擋項目在 P1 內修正重審，最多 3 輪。其他步驟失敗交給人。
- **可寫範圍**：可寫 `artifacts/base/`、`artifacts/baseline/`。FW source：機械替換只寫專案設定列的生成區，移植只改專案設定列的移植範圍；其他 FW source 一律禁止。
- **人怎麼參與**：P1 內不參與；GB 核准。
- **獨立性要求**：移植審查由另一個 session 執行，最好換一個模型（比照 M6）。

**為什麼移植在 P1，不交給模組**：建立新專案的 code base 不是任何一張 CR 的內容，而 P2 要把範圍對到新專案的 code、P3 要用新 IC 的記憶體用量定預算、M2 要用基底 image 證明判別能力，基底都必須在 P2 之前存在。P1 改 code 的限制（確定性的機械替換、限定範圍的移植、獨立審查、GB 逐項處置 FAIL）是為了讓量出來的基線仍然可以當對照組。

## 實作（待展開）

- **執行者**：起點檢查、機械替換、build 與測試由串接層派工的工具執行；移植由 AI；移植審查由另一個 AI session。
- **執行方式**：工具步驟是純程式；移植每輪一個新 session（比照 M4）；審查是無人在旁的單次執行。
- **工具**：
  - build 與驗證：ds5-build／andes-build、remote-ice、bootcode-qa。
  - 機械替換：bcgen 或 script，依生成配方執行；bcgen 只做機械式的產出，做不到的部分由移植步驟補。外部來源快照、register 版本辨識與差異查詢、HW spec 查詢等工具另外設計（[framework/08 §8.2](../framework/08_open_questions.md#82-實作待決)）。
  - 開始時用 bcgen 的唯讀 JSON CLI 核對盤點清單與 G0 核准的必要／排除處置；建置路線步驟 3 再接 MCP 與服務（[impl/bcgen](../impl/bcgen.md)）。
- **待展開議題**：
  - image 載入與跑測試的串接方式，和 M5 是同一個問題（見 [M5](M5.md)）。
  - 移植項目清單的格式，以及審查怎麼核對每處修改的依據。
  - 外部來源換版（例如 HW 更新 register）時，重新機械替換後怎麼把既有的移植修改重新套上。
