# P1 基底與基線建立

## 介面（框架固定）

- **目的**：從 G0 核准的起點與程式碼建立設定，建立這個專案可以用的 code base（基底），再量出對照基準。之後出現 FAIL 時，才分得出是新改動造成的，還是基底原本就是這樣。
- **層級**：專案
- **由誰做**：第 1、2、5 步是工具步驟，由串接層執行；第 3 步移植、第 4 步移植審查是外部互動，由人開 agent 照 skill 完成，兩步分兩次開工（[framework/04 §4.2](../framework/04_rules.md#42-兩種執行方式)）。
- **從哪裡進來**：
  - G0 核准之後。
  - 改基底、平台或 toolchain（包括程式碼建立設定或外部來源換版），P0 重做之後。
  - GB 判定某個基線 FAIL 是移植問題。
  - 人指定重做（例如 P2 發現基線缺既有功能的測試結果）。
- **輸入**：
  - P0 的四份文件（有 G0 核准）。專案設定的「起點與程式碼建立設定」決定怎麼建立基底；範圍清單裡的既有功能（標成保留、修改、移除的項目）就是基線要跑的對象。
  - 程式碼建立設定列的外部來源快照。P1 只讀快照，不讀原始位置。
- **做什麼**（依序）：
  1. **起點檢查**：起點 commit 上，必要 build 設定都 build 得過；同時用 checker 重新核對 build 設定的處置。只確認起點可用，不當成基線。
  2. **機械替換**（有程式碼建立設定時）：串接層依程式碼建立設定執行確定性工具（bcgen 或 script），把外部來源的內容換進 code、建立新 IC 的目錄與 build 設定，commit 成一個獨立的 commit。只寫專案設定列的生成區與起始複製區；同一份建立設定重跑必須得到相同的結果。
  3. **移植**（有程式碼建立設定時）：機械替換做不到的部分由 AI 修改，例如 register 改變後受影響的 HAL 與初始化。只改專案設定列的移植範圍；每處修改在移植說明裡寫明依據（程式碼建立設定的項目、register 差異或 HW spec 的出處）。和機械替換的 commit 分開。
  4. **移植審查**（有移植修改時）：另一個執行者審查移植的 diff。
  5. **量基線**：在基底上 build 所有必要設定，在驗證平台跑 openBCT 既有的測試項目（2026-10-22，依使用者決定：這些既有測項全部都要通過；CR 的測項由 M2 另外新增）。很多 bootcode 測項要先用 burner 把 FW、ID page 寫進 NAND，或要拿 burner 驗帶入與跳轉，所以基線也要有一版能用的 burner，並記下它的 image hash（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。
  - 沒有程式碼建立設定的專案（例如同一顆 IC 的改版），跳過第 2–4 步，基底就是起點 commit。
- **輸出**：
  - 基底 commit：在專案層工作 branch 上（[framework/03 §3.7](../framework/03_artifacts.md#37-存放位置)）。
  - 基底建立紀錄（`artifacts/base/`）：生成紀錄（建立設定、工具與版本、機械替換 commit、重跑比對結果）、移植說明、移植審查報告。
  - 基線報告（`artifacts/baseline/`）：每個必要 build 設定的結果、image hash、記憶體用量；既有功能的測試結果；基線待處理清單（保留的既有功能在基底上 FAIL 的項目，附證據）。
- **擋關檢查**：build 設定都有處置（開始時）、build 零警告（起點與基底的所有必要設定）、機械替換可重現、只寫在允許範圍內、審查沒有未處置的阻擋項目（移植審查）、既有功能已量測。
- **出口關卡**：**只在基線待處理清單不是空的時候**經 GB，由人逐項決定：

  | 決定 | 之後怎麼走 |
  | :---- | :---- |
  | 移植問題 | 回第 3 步修正，計入移植輪數；修正後重量基線 |
  | 新 IC 本來就不同，這版要改 | 回 P0 把這項既有功能改標「修改」，重開 G0，之後交給模組處理；基線保留這個 FAIL 結果 |
  | 接受，這版不處理 | 記錄理由；P5 把它當成基底原本的狀態 |

  待處理清單是空的，P1 擋關檢查都過就直接完成。
- **失敗時**：
  - 程式碼建立設定不齊全或有誤、移植需要改移植範圍以外的檔案 → 交給人，通常回 P0 補齊建立設定；不能自行擴大範圍。
  - 移植後 build 不過或審查有阻擋項目 → 在第 3 步重做，最多 3 輪：上限由移植 skill 遵守，累計由串接層寫進工作包，超過只提示。
  - 機械替換的工具出錯或重跑結果不同、起點本身 build 不過、環境問題 → 交給人。
  - P1 不自行把失敗的必要設定改成排除。
- **可寫範圍**：可寫 `artifacts/base/`、`artifacts/baseline/`。FW source：機械替換只寫生成區與起始複製區，移植只改移植範圍（不能落在生成區）；其他 FW source 一律禁止。

**為什麼移植在 P1，不交給模組**：建立新專案的 code base 不是任何一張 CR 的內容，而 P2 要把範圍對到新專案的 code、定記憶體預算，M2 要用基底 image 證明判別能力，基底都必須在 P2 之前存在。P1 改 code 的限制（確定性的機械替換、限定範圍的移植、獨立審查、FAIL 交人處置）是為了讓量出來的基線仍然可以當對照組。

## 實作（待展開）

- **執行者**：起點檢查、機械替換、build 與測試由串接層的工具執行；移植由人開的 agent 照移植 skill 完成；移植審查是另一次開工，由審查 skill 完成。
- **工具**：
  - build 與驗證：ds5-build／andes-build、remote-ice、bootcode-qa。
  - 機械替換：bcgen 或 script，直接讀專案設定的建立設定區塊執行（[impl/recipe](../impl/recipe.md)、[impl/bcgen](../impl/bcgen.md)）。
  - build 設定處置的核對：串接層的 checker（共用待辦 OBC-030），和 P0 用同一個。
- **待展開議題**：
  - image 載入與跑測試的串接方式，和 M5 是同一個問題（見 [M5](M5.md)）。
  - 外部來源換版（例如 HW 更新 register）時，重新機械替換後怎麼把既有的移植修改重新套上。
