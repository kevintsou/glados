# P2 規劃

## 介面（框架固定）

- **目的**：把 G0 核准的範圍清單對到基底的 code、切成模組，定模組的對外介面與記憶體預算，讓每個模組能各自往下走；過程中發現 CR 本身不夠用時，在 P2 內整理 CR。範圍本身（做不做、留不留）在 P0 已經決定，P2 不重新討論。v0.9 起原本的 P3 架構與介面併進這一站。
- **層級**：專案
- **由誰做**：外部互動。
- **從哪裡進來**：
  - P1 完成之後（有 GB 時經 GB 處置）。
  - C＋GC 接受「全新功能」或「改模組介面或記憶體預算」的變更。
  - 人指定重做（例如模組遇到介面衝突、模組切分有誤）。
  - G1 核准前，外部來源同步發現既有 CR 或 spec 頁的內容被改（新 CR、取消 CR 回 P0）。
- **輸入**：
  - 範圍清單（有 G0 核准；G1 後經 C 改版的由 GC 核准）。
  - 來源快照。
  - 基底 commit 與基線報告。
  - 專案設定的 code 模組對照、共用層規則、衝突熱點、記憶體上限、「寫進 Jira」。
- **輸出**：
  - 差異分析（`artifacts/delta.md`）：
    - 範圍清單裡標成新增、修改、移除的每一項：對到哪些 code、屬於哪個模組。
    - 每個模組的 code 範圍，列到檔案。
    - 受影響的既有功能（regression 範圍）。
    - 模組之間的相依與執行順序；改到的檔案有重疊、或要用到另一個模組實作結果的模組，標為序列（[framework/02 §2.6](../framework/02_workflow.md#26-模組之間)）。
  - 架構文件（`artifacts/arch.md`）：
    - 每個模組的對外介面，用編號條目寫，讓 M1、M4 可以引用。
    - 記憶體預算分配：每個必要 build 設定各分一次，總和不超過該設定的上限；同一個模組在不同設定裡的份量可能不同（[framework/09](../framework/09_build_configurations.md)）。
    - 錯誤碼表與 boot flow 的變更。
  - CR 修訂紀錄（`artifacts/cr_revisions.md`，有修訂時才有）：每一項寫明對應的範圍清單項目、原內容與定案內容、理由；改變需求內容的修訂由專案設定的「CR 修改決定人」定案。
- **擋關檢查**：無（內容由 G1 核准）。
- **收件檢查**：見 [framework/05 §5.5](../framework/05_checks.md#55-收件檢查) 的 P2 列。
- **出口關卡**：G1 規劃核准。
- **失敗時**：
  - 對不到 code 是因為專案設定的 code 模組對照沒涵蓋，或範圍清單本身有問題（做不到、互相矛盾、移除 A 但保留的 B 依賴 A）→ 回 P0，重開 G0。
  - 需要 HW、SOC 等外部資訊 → 登記待確認事項，轉為「等外部回覆」。
  - 基線缺既有功能的測試結果 → 回 P1。
  - 行為細節不清楚，但不影響對到哪段 code 或介面 → 不擋 P2，寫進交接說明交給 M1。
- **可寫範圍**：可寫 `artifacts/delta.md`、`artifacts/arch.md`、`artifacts/cr_revisions.md` 與交接說明；不能改來源快照（寫回 Jira 與重抓快照由工具執行）；禁止改 FW source。

**CR 修訂的界線**：

- 拆分（一張 CR 改到兩個模組）、補 CR（範圍清單的項目沒有對應的 CR）、澄清（CR 寫得不夠判斷要改哪段 code）可以在 P2 定案。
- 改變需求內容的修訂（例如 CR 假設的機制在 code 裡不存在），由 CR 修改決定人定案。
- 會改到範圍清單標記的（例如真的是新功能，或某一項這版不做了），P2 不能決定，回 P0。
- 專案設定允許寫回 Jira 時，定案就由工具寫回並重抓受改項目的快照；不允許時（例如有雙向隔離的 E39）只記在 CR 修訂紀錄。
- G1 核准後，新的需求變更一律走 C＋GC（[framework/04 §4.6](../framework/04_rules.md#46-需求變更)）。

## 實作（待展開）

- **執行者**：人＋agent（強模型）；分析時可以把範圍項目分給多個 subagent 平行做。
- **工具**：
  - 分析：GitLab MCP、bootcode-qa、pyconvert（eFuse／BCFG 欄位與 layout）。
  - 寫 CR：新的「CR 撰寫」skill，照 CR 範本（E39 是 `SDKBOOT-2420`）產出內容；做法參考 openBCT 的 `write-jira-desc`，先從 code 挖出事實，再用 bct-grill-me 讓人定案。
  - 寫回 Jira：工具在定案後呼叫 Jira REST API 寫回並核對結果；失敗或內容衝突就交給人；AI 不直接寫 Jira。
