# P2 差異分析

## 介面（框架固定）

- **目的**：把 G0 核准的範圍清單對到 code 位置，再切成模組；過程中發現 CR 本身不夠用時，在 P2 內整理 CR。範圍本身（做不做、留不留）在 P0 已經決定，P2 不重新討論。
- **層級**：專案
- **從哪裡進來**：
  - P1 完成之後。
  - C 變更處理判定「全新功能，不碰既有模組」→ 在 P2 追加模組。
  - 第一次通過 G1 前，外部來源同步發現既有 CR 或 spec 頁的內容被改（新 CR、取消 CR 回 P0）。
- **輸入**：
  - 範圍清單（有 G0 核准）。
  - 來源快照（第一次通過 G1 前由 P0／P2 整理採用的版本；之後使用需求基準，只有經 C＋GC 接受的需求變更才能產生採用的新版；不直接讀 Jira／Confluence）。
  - 基線報告。
  - 專案設定的 code 模組對照、共用層規則、衝突熱點，以及「CR 修訂寫回 Jira」。
- **輸出**：
  - 差異分析（`artifacts/delta.md`），至少包括：
    - 範圍清單裡標成新增、修改、移除的每一項一列：對到哪些 code、屬於哪個模組。
    - 每個模組的 code 範圍。
    - 受影響的既有功能（regression 範圍）。
    - 模組之間的相依與執行順序；改到衝突熱點檔案的模組標為序列。
  - CR 修訂紀錄（`artifacts/cr_revisions.md`，有修訂時才有）：每一項寫明類型（見下方 P2b）、對應的範圍清單項目、理由與 code 上的證據、原內容與定案內容、P2b 的確認結果、寫回狀態及相關來源快照版本。
- **出口檢查**：範圍清單都有歸屬、CR 修訂都有歸屬、需求來源已整理、模組順序已定、regression 範圍已定。
- **出口關卡**：G1 範圍核准（審核整理後的來源快照、CR 修訂紀錄與差異分析，綁定確切版本與 hash，建立需求基準）。
- **失敗退回**：見下方「輸入不足」。
- **迴圈上限**：待定。
- **可寫範圍**：可寫 `artifacts/delta.md`、`artifacts/cr_revisions.md`；不能改來源快照（寫回 Jira 與重抓快照由工具執行）；禁止改 FW source。
- **人怎麼參與**：P2a 不參與；P2b 與 AI 一起討論（有 CR 修訂提案或外部修改時才進行）；G1 核准。
- **獨立性要求**：無。

### P2a 與 P2b

| 段落 | 誰做 | 做什麼 |
| :---- | :---- | :---- |
| P2a 分析 | AI，無人在旁 | 把範圍清單對到 code、切成模組；發現 CR 不夠用時，列出「CR 修訂提案」；外部來源同步發現的別人的修改也一起列出 |
| P2b CR 整理 | 人＋AI，互動式；有修訂提案或外部修改時才進行 | 一題一題確認修訂提案與外部修改；「修改」由專案設定的「CR 修改決定人」定案（預設是 CR 負責人）。確認後 P2a 用修訂後的內容接續 |

CR 修訂紀錄的每一項分五類，前四類是 GLADOS 提出的修訂，第五類是別人的修改：

| 類型 | 例子 | 本質 |
| :---- | :---- | :---- |
| 拆分 | 一張 CR 同時改到兩個模組（E39 的 2259 DICE UDS 同時改 `dice.c` 與 `lcp.c`） | 需求不變 |
| 補 CR | 範圍清單裡的項目沒有對應的 CR：P0 決定「移除」的既有功能、某張 CR 需要先做的前置修改 | 範圍不變 |
| 澄清 | CR 寫得不夠，判斷不出要改哪段 code | 需求不變 |
| 修改 | CR 和 code 現況矛盾，例如假設的機制在 code 裡不存在 | 需求內容改變 |
| 外部修改 | G0 之後、第一次通過 G1 前，別人在 Jira／Confluence 上改了 CR 內容或 spec 頁（外部來源同步發現） | 依內容而定；經 P2b 由人確認才採用，AI 不能自己採用；已經在 Jira 上，不需要寫回 |

P2b 的界線：

- **會改到範圍清單標記的，P2b 不能決定**：例如真的是新功能，或某一項這版不做了 → 退回 P0，重開 G0（只審差異）。
- **行為細節的澄清留給 M1**：P2b 只處理卡住「對到 code、切模組」的問題。
- **P2b 定案就更新，不等 G1**：專案設定允許寫回 Jira 時，由工具立即寫回並核對結果、重抓受改項目的來源快照；不允許時（例如有雙向隔離的 E39）只更新內部 CR 修訂紀錄。每項修訂保留原內容、定案內容、P2b 確認結果，以及寫回狀態和快照版本，避免下游把已寫回的同一修訂再套一次。
- **第一次通過 G1 前，外部修改也在 P0／P2 整理**：不區分誰提出。新 CR、取消 CR，以及會改範圍、起點或平台的，回 P0 重開 G0；其餘記成「外部修改」，在 P2b 由人確認。行為細節仍留給 M1。
- **重抓只接納已確認的差異**：工具寫回 CR-A 時若發現 CR-A 又被別人改了，先回 P2b 確認，不覆蓋對方的修改；同時發現 CR-B 有修改，另列待整理差異，不能一起視為已定案。
- **G1 審核整理後的結果**：P2b 定案 → 工具更新 Jira／內部修訂紀錄與快照 → P2a 完成分析 → G1 審核。G1 的審查包逐項列出 CR 修訂紀錄的每一項（含外部修改），讓核准人逐項表態；送出前再同步一次，有新的來源差異就作廢重來。下游讀 G1 核准的「來源快照＋CR 修訂紀錄」。G1 未通過就留在 P2 修正；若需要再改 CR，回 P2b，保留每次修訂歷史。
- **第一次通過 G1 後的需求變更都走 C＋GC**：即使因變更或退回而重跑 P2，也只能整理 GC 已接受範圍內的內容；另有新增或修改需求時再走 C，不能用 P2b 直接接受（[framework/04 §4.6](../framework/04_rules.md#46-c-變更處理)）。

### 輸入不足

定義：**P2 有某個必要輸出填不出來，而且原因是某個輸入缺漏或有問題。** 缺的是哪個輸入，就退回產出那個輸入的地方（[framework/04 §4.5](../framework/04_rules.md#45-r-失敗分類) 的「輸入不足」）：

| 填不出來的輸出 | 缺的是 | 去哪裡 |
| :---- | :---- | :---- |
| 某一項對不到 code | 專案設定的 code 模組對照沒涵蓋 | 退回 P0 改專案設定，重開 G0（只審差異）；只有用到 code 模組對照的 P2、P3 要重走，P1 基線不受影響 |
| 某一項對不到 code | CR 內容不夠判斷 | P2b CR 整理 |
| 某一項做不到、兩項互相矛盾，或移除 A 但保留的 B 依賴 A | 範圍清單本身 | 退回 P0 改範圍清單，重開 G0（只審差異） |
| 需要 HW、SOC 等外部資訊才能判斷 | 外部資訊 | 登記待確認事項，節點轉為「等待外部回覆」 |
| regression 範圍定不出來 | 基線報告缺既有功能的測試結果 | 退回 P1 |
| 行為細節不清楚，但不影響對到哪段 code | **不算輸入不足** | 寫進交接清單的 `notes_for_next` 交給 M1，不擋 P2 |

- **執行方式**：P2a 無人在旁執行，把範圍項目分給多個 subagent 平行分析；P2b 互動式 session，用 grill-me 的方式一次問一個問題。
- **工具**：

  - 寫 CR：新的「CR 撰寫」skill，照 CR 範本（E39 是 `SDKBOOT-2420`）產出內容。做法參考 openBCT 的 `write-jira-desc`（寫測項的 Jira description）：先從 code 挖出事實，再用 grill-me 讓人定案，agent 不自己編造意圖。
