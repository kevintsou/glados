# P0 專案啟動

## 介面（框架固定）

- **目的**：定這個專案的範圍（做不做、留不留）、起點、程式碼建立設定與環境，讓後面每一站都有固定的依據。
- **層級**：專案
- **由誰做**：外部互動。串接層開工（準備隔離工作區、來源快照與工作包），人和 agent 一起完成，提交後串接層收件（[framework/04 §4.2](../framework/04_rules.md#42-兩種執行方式)）。
- **從哪裡進來**：
  - 新專案。
  - 改基底、平台或 toolchain（C＋GC 接受後）。
  - P2 發現範圍清單或專案設定要改。
  - P1 判定程式碼建立設定不齊全或有誤、移植需要擴大範圍；GB 決定某個基線 FAIL 這版要改（範圍清單改標「修改」）。
  - G1 核准前，外部來源同步發現 Epic 底下多了新 CR，或 CR 被取消。
- **輸入**：
  - 來源快照：由工具依專案設定的 Jira Epic、feature list 與 spec 頁 ID 抓下來（[framework/03 §3.2](../framework/03_artifacts.md#32-來源快照)）。
  - test plan：P4 整合驗證照它跑，取得方式和 feature list 一樣（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。
  - feature list：bootcode 和 sandaru／burner 各一份，依這顆 IC 的 label 篩出適用項目（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。feature list 加上 CR，是 bootcode 和 burner 基本架構的依據。
  - 起點 repo 與 branch／commit：必須是已發佈或已驗證的版本，例如 release branch 或 tag。
  - 外部來源快照（有程式碼建立設定時）：例如新 IC 的 register、HW spec；svn、git 或資料夾，資料夾要定版複製並記錄逐檔 hash（[framework/07](../framework/07_project_profile.md)）。
  - 起點 code 與知識庫：用來盤點既有功能。
  - 專案設定範本（[framework/07](../framework/07_project_profile.md)）。
- **輸出**：
  - 專案說明（`project.md`）：起點 commit 與它是已發佈或已驗證版本的依據、禁止 agent 看到的 branch。
  - 範圍清單（`scope.md`）：每一項一列，包括項目（一張 CR、一頁 spec 的需求、一個 feature list 項目，或一個既有功能）、屬於哪支程式（bootcode、burner，或兩邊共用）、標記（新增、修改、保留、移除、這版不做）、來源（引用來源快照的項目，或既有功能所在的 code 位置）、理由（「移除」與「這版不做」必填）。
  - 專案設定（`profile.json`）：依 framework/07 的欄位填寫，不放密碼、token 或本機路徑。新 IC 或要換 register 的專案，「起點與程式碼建立設定」就是 P1 建立基底的輸入（格式見 [impl/recipe](../impl/recipe.md)）。
  - 環境清單（`environment.json`）：這個專案需要的 toolchain、生成工具、測試工具、skill、MCP、知識庫。**影響 build 的項目**（toolchain、生成工具）附固定版本；skill、MCP、知識庫只記建議使用的版本，執行時用了哪一版記在執行紀錄（[framework/04 §4.4](../framework/04_rules.md#44-上游改版與重做)）。
- **擋關檢查**：隔離設定正確、來源快照完整、範圍清單涵蓋所有 CR 與 feature list 項目、build 設定都有處置、建立設定是否齊全（有程式碼建立設定時）。
- **收件檢查**：見 [framework/05 §5.5](../framework/05_checks.md#55-收件檢查) 的 P0 列。
- **出口關卡**：G0 啟動核准。
- **失敗時**：檢查沒過交還給人補齊；起點取不到、環境需要人處理時，在開工時就交給人。
- **可寫範圍**：可寫 `project.md`、`scope.md`、`profile.json`、`environment.json` 與交接說明；不能改來源快照（由工具產生）；禁止改 FW source。

**怎麼進行**：agent 先讀來源快照、盤點起點 code、草擬四份文件，再和人一題一題討論：哪些 CR 這版做、既有功能哪些留哪些拿掉、burner 需要哪些功能與各自怎麼實作（依 burner feature list，討論項目見 [framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）、起點、程式碼建立設定與環境。草擬程式碼建立設定時，先辨認起點 code 用的是外部來源的哪個版本，再依新 IC 的來源列出要換的 block、code 目錄對照、生成區、起始複製區與移植範圍的候選；對不上、新 IC 缺少的 block、需要人判斷的範圍，都要問人，不能自行推定。

**和 P2、M1 的分工**：P0 決定「做不做、留不留」；P2 把核准的範圍對到 code、切成模組、定介面；M1 決定每個模組的行為細節與驗收標準。三站不重複討論同一件事。

## 實作（待展開）

- **執行者**：人＋agent（建議使用 bct-p0 skill）。
- **工具**：
  - 來源快照：直接呼叫 Jira／Confluence REST API 的 script，以 openBCT 的 `scripts/sync_jira_ic.py` 為基礎改寫（指定 Epic、逐張抓完整內容與全部留言、算 hash、比對總數）。不用 MCP 抓快照，因為 mcp-atlassian 的 `searchIssues` 只保留最後 3 則留言，description 也會先轉成純文字。**憑證**（2026-10-19，依使用者決定）：用目前使用 GLADOS 的人自己的 Jira／Confluence Personal Access Token，不另開服務帳號；token 存在各自電腦的環境變數或 Windows 認證管理員，不進 repo、快照、log 或工作包；快照記下是誰抓的。工具只發讀取請求；使用者看不到的 CR 會讓「來源快照完整」擋下，不會默默漏掉。
  - 哪些 code 屬於哪支程式：工具從 build 設定算出每個檔案屬於 bootcode、burner 或兩邊共用，P0 給人確認（[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）。
  - 盤點起點：agent 直接讀指定起點 commit 的 build 設定（ARM 的 `.cproject`、Andes 的 build 設定）、feature 條件與 code 引用；不用 bcgen 盤點（[impl/bcgen](../impl/bcgen.md)）。「build 設定都有處置」由串接層的 checker 獨立列舉起點的 build 設定、比對專案設定（共用待辦 OBC-030）。
  - 外部來源與程式碼建立設定：外部來源快照、register 版本辨識與差異查詢、HW spec 查詢另外設計（[framework/08 §8.2](../framework/08_open_questions.md#82-實作待決)）；建立設定直接寫進專案設定（[impl/recipe](../impl/recipe.md)）。
  - 討論：bct-p0 skill（草擬四份文件，討論時叫用 bct-grill-me 一次問一個問題，共用待辦 SK-007）、Atlassian MCP（查線上內容找線索）、bootcode-qa。
- **待展開議題**：
  - **既有功能從哪裡盤點**：主要來源是 feature list（2026-10-28 使用者說明，[framework/09 §9.4](../framework/09_build_configurations.md#94-sandaruburner-是專案的一部分)）；其他候選有起點 code 的 build 設定與 feature 條件、知識庫的 `bootcode_concepts.md`、Jira 上既有的測試項目（例如 E39 Epic 底下的 sub-task）。feature list 和 code 對不上（code 有、list 沒有，或反過來）要問人。code 裡有、條件啟用、已有實測要分開記錄；共用 source 裡其他 IC 的功能不自動算進來；盤點不到的項目要問人。
  - **隔離設定怎麼檢查**：工作區 repo 的 branch 清單可以自動核對；agent token 的權限範圍可能要人工確認。
