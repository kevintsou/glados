# P0 專案啟動

## 介面（框架固定）

- **目的**：定這個專案的範圍（做不做、留不留）、起點、生成配方與環境，讓後面每一站都有固定的依據。
- **層級**：專案
- **從哪裡進來**：
  - 新專案。
  - C 變更處理判定「改基底、平台或 toolchain」。
  - P2 發現範圍清單或專案設定要改。
  - P1 判定生成配方不完整或有誤、移植需要擴大範圍；GB 決定某個基線 FAIL 這版要改（範圍清單改標「修改」）。
  - 第一次通過 G1 前，外部來源同步發現 Epic 底下多了新 CR，或 CR 被 reject、取消。
- **輸入**：
  - 來源快照：由工具依專案設定的 Jira Epic 與 spec 頁 ID 抓下來（[framework/03 §3.2](../framework/03_artifacts.md#32-編號版本與-hash)）。P0 只讀快照；第一次通過 G1 前，Jira／Confluence 的新增或修改在 P0／P2 整理，再請工具產生快照新版。G1 後回到 P0 時，只採用經 C＋GC 接受的需求變更。
  - 起點 repo 與 branch／commit：必須是已發佈或已驗證的版本，例如 release branch 或 tag。
  - 外部來源快照（有生成配方時）：例如新 IC 的 register、HW spec。由工具依專案設定列的來源產生；來源類型可以是 svn、git 或資料夾，資料夾沒有版本號，要在定版時複製並記錄逐檔 hash（[framework/07](../framework/07_project_profile.md)）。P0 只讀快照。
  - 起點 code 與知識庫：用來盤點既有功能。
  - 專案設定範本（[framework/07](../framework/07_project_profile.md)）。
  - 各節點實作宣告需要的 skill、MCP、工具：用來列環境清單。
- **輸出**：
  - 專案說明（`project.md`）：起點 commit 與它是已發佈或已驗證版本的依據、禁止 agent 看到的 branch。
  - 範圍清單（`scope.md`）：每一項一列，至少包括
    - 項目：一張 CR、一頁 spec 的需求，或一個既有功能；
    - 標記：新增、修改、保留、移除、這版不做；
    - 來源：引用來源快照的項目，或既有功能所在的 code 與知識庫位置；
    - 理由：「移除」與「這版不做」必填。
  - 專案設定（`profile.json`）：依 framework/07 的欄位填寫，不放機器路徑、密碼或 token。新 IC 或要換 register 的專案，「起點與生成配方」欄位就是 P1 建立基底的依據：外部來源與版本、register 各 block 的版本與 code 目錄對照、生成區、移植範圍、新舊 build 設定的對應。
  - 環境清單（`environment.json`）：這個專案需要的 skill、MCP、工具、toolchain、知識庫，每一項附固定的版本，並標明類別：影響 build、影響驗證，或只影響 AI（改版時會過期什麼依類別而定，見 [framework/04 §4.4](../framework/04_rules.md#44-過期與重新進入)）。列哪些項目，由專案設定（例如 ARM 就列 ds5-build）和各節點的實作決定。
- **出口檢查**：來源快照完整、範圍清單完整、專案設定完整、起點版本可取得、環境清單版本已固定、環境就緒、隔離設定正確。
- **出口關卡**：G0 啟動核准（核准專案說明、範圍清單、專案設定、環境清單的版本）。G0 固定專案範圍、起點與環境；CR 變更走 C 的分界是第一次通過 G1 建立的需求基準（[framework/02 §2.4](../framework/02_workflow.md#24-人工關卡)）。
- **失敗退回**：輸入不足、起點不能用或環境沒就緒 → 留在 P0 補齊；需要人處理環境，或仍無法解決 → 交給人。
- **迴圈上限**：P0a 2 輪；P0b 不設（人在場）。
- **可寫範圍**：可寫 `project.md`、`scope.md`、`profile.json`、`environment.json`；不能改來源快照（由工具產生）；禁止改 FW source。
- **人怎麼參與**：P0a 不參與；P0b 與 AI 一起討論。
- **獨立性要求**：無。

### P0a 與 P0b

| 段落 | 誰做 | 做什麼 |
| :---- | :---- | :---- |
| P0a 草擬 | AI，無人在旁 | 讀來源快照；盤點起點 code 的既有功能；草擬範圍清單、專案設定（含生成配方）、環境清單；列出要問人的問題 |
| P0b 討論 | 人＋AI，互動式 | 對著來源快照與 P0a 的草稿，一題一題討論：哪些 CR 這版做、既有功能哪些留哪些拿掉、起點、生成配方與環境。定案後送 G0 |

**生成配方怎麼草擬**：P0a 先辨認起點 code 用的是外部來源的哪個版本（例如每個 register block 對到哪一版），再依新 IC 的來源列出要換的 block、code 目錄對照、生成區與移植範圍的候選。對不上、新 IC 缺少的 block、需要人判斷的範圍，都列成問題交給 P0b，不能自行推定。

P0a 可保存四份候選草稿，P0b 可依討論更新；保存草稿不代表核准。人的確認針對範圍與設定決定，G0 核准四份產出的確切版本。

**和 P2、M1 的分工**：P0 決定「做不做、留不留」；P2 把核准的範圍對到 code、切成模組；M1 決定每個模組的行為細節。三站不重複討論同一件事。

## 實作（待展開）

- **執行者**：P0a 是 AI＋工具；P0b 是人＋AI。
- **執行方式**：P0a 無人在旁執行；P0b 互動式 session。
- **工具**：
  - 來源快照：直接呼叫 Jira／Confluence REST API 的 script，以 openBCT 的 `scripts/sync_jira_ic.py` 為基礎改寫（指定 Epic、逐張抓完整內容與全部留言、算 hash、比對總數）。不用 MCP 抓快照，因為 mcp-atlassian 的 `searchIssues` 只保留最後 3 則留言，description 也會先轉成純文字。
  - 盤點起點：bcgen 的唯讀 JSON 命令列（AI 節點的命令允許清單只列唯讀子指令，不做 MCP）。P0a 盤點 CPU、build target、記憶體、eFuse、register 與功能線索，產生專案設定候選資料；P0b 查功能相依、code 參考與過往問題，確認每個 target 的必要／排除處置。只能讀指定的起點 commit，AI 自行查到的結果只供參考；正式檢查由扮演串接層的人或服務獨立執行 CLI 留證據。唯讀介面不代寫 P0 產出或存工具設定（[impl/bcgen](../impl/bcgen.md)）。
  - 外部來源與生成配方：外部來源快照（svn、git、資料夾）、register 版本辨識與結構化差異查詢、HW spec 查詢，另外設計（[framework/08 §8.2](../framework/08_open_questions.md#82-實作待決)）。
  - 討論：grill-me（一次問一個問題）、Atlassian MCP（討論時查線上內容找線索）、bootcode-qa。
- **待展開議題**：
  - **既有功能從哪裡盤點**：候選來源有 bcgen 的起點盤點、知識庫的 `bootcode_concepts.md`、起點 code、Jira 上既有的測試項目（例如 E39 Epic 底下的 sub-task）。bcgen 的功能清單不代表起點的全部既有功能，盤點不到的項目要列成問題交給 P0b。
  - **知識庫怎麼真的鎖在環境清單的版本**（2026-10-07 討論）：bct_knowledge_base 的安裝程式會把 `Knowledge_Base/` 複製到全機共用的 `~/.claude/skills/bootcode-qa/database`；bootcode-qa 的 `vector_db/` 也是各機器本機建的，不進 git。同一台機器上只要有人更新，執行中的專案看到的內容就跟著變。要真的鎖住，節點用的 skill 與知識庫路徑需要「每個專案一份」。
  - **環境就緒怎麼檢查**：每一類項目的檢查方式不同，例如 skill 看安裝的版本、MCP 要能連線、ICE 與 FPGA 要連得上。
  - **隔離設定怎麼檢查**：工作區 repo 的 branch 清單可以自動核對；agent token 的權限範圍可能要人工確認。
