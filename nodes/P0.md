# P0 專案啟動

## 介面（框架固定）

- **目的**：定這個專案的範圍（做不做、留不留）、起點與環境，讓後面每一站都有固定的依據。
- **層級**：專案
- **從哪裡進來**：
  - 新專案。
  - C 變更處理判定「改基底、平台或 toolchain」。
  - P2 發現範圍清單或專案設定要改。
- **輸入**：
  - 來源快照：由工具依專案設定的 Jira Epic 與 spec 頁 ID 抓下來（[framework/03 §3.2](../framework/03_artifacts.md#32-編號版本與-hash)）。P0 只讀快照；第一次通過 G1 前，Jira／Confluence 的新增或修改在 P0／P2 整理，再請工具產生快照新版。G1 後回到 P0 時，只採用經 C＋GC 接受的需求變更。
  - 起點 repo 與 branch／commit。
  - 起點 code 與知識庫：用來盤點既有功能。
  - 專案設定範本（[framework/07](../framework/07_project_profile.md)）。
  - 各節點實作宣告需要的 skill、MCP、工具：用來列環境清單。
- **輸出**：
  - 專案說明（`project.md`）：起點 commit、禁止 agent 看到的 branch；G0 核准後記下範圍凍結點。
  - 範圍清單（`scope.md`）：每一項一列，至少包括
    - 項目：一張 CR、一頁 spec 的需求，或一個既有功能；
    - 標記：新增、修改、保留、移除、這版不做；
    - 來源：引用來源快照的項目，或既有功能所在的 code 與知識庫位置；
    - 理由：「移除」與「這版不做」必填。
  - 專案設定（`profile.json`）：依 framework/07 的欄位填寫，不放機器路徑、密碼或 token。
  - 環境清單（`environment.json`）：這個專案需要的 skill、MCP、工具、toolchain、知識庫，每一項附固定的版本。列哪些項目，由專案設定（例如 ARM 就列 ds5-build）和各節點的實作決定。
- **出口檢查**：來源快照完整、範圍清單完整、專案設定完整、起點版本可取得、環境清單版本已固定、環境就緒、隔離設定正確。
- **出口關卡**：G0 啟動核准（核准專案說明、範圍清單、專案設定、環境清單的版本）。G0 核准時間就是範圍凍結點，固定專案範圍、起點與環境；CR 變更走 C 的分界是第一次通過 G1（[framework/02 §2.4](../framework/02_workflow.md#24-人工關卡)）。
- **失敗退回**：資訊不足、起點不能用或環境沒就緒 → 留在 P0 補齊；需要人處理環境，或仍無法解決 → 交給人。
- **迴圈上限**：待定。
- **可寫範圍**：可寫 `project.md`、`scope.md`、`profile.json`、`environment.json`；不能改來源快照（由工具產生）；禁止改 FW source。
- **人怎麼參與**：P0a 不參與；P0b 與 AI 一起討論。
- **獨立性要求**：無。

### P0a 與 P0b

| 段落 | 誰做 | 做什麼 |
| :---- | :---- | :---- |
| P0a 草擬 | AI，無人在旁 | 讀來源快照；盤點起點 code 的既有功能；草擬範圍清單、專案設定、環境清單；列出要問人的問題 |
| P0b 討論 | 人＋AI，互動式 | 對著來源快照與 P0a 的草稿，一題一題討論：哪些 CR 這版做、既有功能哪些留哪些拿掉、起點與環境。定案後送 G0 |

**和 P2、M1 的分工**：P0 決定「做不做、留不留」；P2 把核准的範圍對到 code、切成模組；M1 決定每個模組的行為細節。三站不重複討論同一件事。

## 實作（待展開）

- **執行者**：P0a 是 AI＋工具；P0b 是人＋AI。
- **執行方式**：P0a 無人在旁執行；P0b 互動式 session。
- **工具**：
  - 來源快照：直接呼叫 Jira／Confluence REST API 的 script，以 openBCT 的 `scripts/sync_jira_ic.py` 為基礎改寫（指定 Epic、逐張抓完整內容與全部留言、算 hash、比對總數）。不用 MCP 抓快照，因為 mcp-atlassian 的 `searchIssues` 只保留最後 3 則留言，description 也會先轉成純文字。
  - 討論：grill-me（一次問一個問題）、Atlassian MCP（討論時查線上內容找線索）、bootcode-qa。
- **待展開議題**：
  - **既有功能從哪裡盤點**：候選來源有知識庫的 `bootcode_concepts.md`、起點 code、Jira 上既有的測試項目（例如 E39 Epic 底下的 sub-task）。
  - **知識庫怎麼真的鎖在環境清單的版本**（2026-10-07 討論）：bct_knowledge_base 的安裝程式會把 `Knowledge_Base/` 複製到全機共用的 `~/.claude/skills/bootcode-qa/database`；bootcode-qa 的 `vector_db/` 也是各機器本機建的，不進 git。同一台機器上只要有人更新，執行中的專案看到的內容就跟著變。要真的鎖住，節點用的 skill 與知識庫路徑需要「每個專案一份」。
  - **環境就緒怎麼檢查**：每一類項目的檢查方式不同，例如 skill 看安裝的版本、MCP 要能連線、ICE 與 FPGA 要連得上。
  - **隔離設定怎麼檢查**：工作區 repo 的 branch 清單可以自動核對；agent token 的權限範圍可能要人工確認。
