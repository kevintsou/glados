# M4 實作與 build

## 介面（框架固定）

- **目的**：依已通過的計畫修改 code，產出可以 build 的 commit。
- **層級**：模組
- **從哪裡進來**：
  - M3 完成。
  - R 失敗分類判定「code 錯」。
- **輸入**：實作計畫（已通過且有效）、測試基準與測試實作（唯讀）、架構文件（記憶體預算）。
- **輸出**：
  - 模組 commit（在模組工作 branch）；commit message 寫對應的計畫步驟。
  - build 證據：由串接層派工 build 出來的 image hash（每個 build 設定一個）、記憶體用量。**放行看的是串接層派工的那次 build，不是節點在 session 裡自己 build 的結果。**
- **出口檢查**：只寫在允許範圍內（只改計畫列出的檔案）、測試沒被動過、追溯關係完整、build 零警告、記憶體在預算內。
- **出口關卡**：無。
- **失敗退回**：
  - build 失敗、有 warning、超出預算 → 留在 M4 重做（計入輪數）。
  - 需要改計畫以外的檔案 → 經 R 失敗分類退回 M3。
- **迴圈上限**：3 輪；連續 3 輪同樣的失敗就交給人。
- **可寫範圍**：只能改計畫列出的 source 檔案；禁止改測試實作、驗收合約、測試基準。
- **人怎麼參與**：不參與。人工也可以直接 commit，但同樣要經過版本同步與上面的檢查（[framework/04 §4.7](../framework/04_rules.md#47-s-版本同步)）。
- **獨立性要求**：無。

## 實作（待展開）

- **執行者**：次強模型＋build 工具。
- **執行方式**：每輪一個新 session，靠 `progress.md` 接續。
- **工具**：ds5-build／andes-build。
- **待展開議題**：
  - [playbook 審查意見](../notes/playbook_kit_review.md)建議的 bootcode 通用紅線（linker script 不准動、所有 polling 都要有 timeout 等），要不要列進可寫範圍的禁止項目或必要規則。
