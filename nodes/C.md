# C 變更分析

## 介面（框架固定）

- **目的**：判斷一張變更 CR 改到哪個產出物、哪些下游要重做、從哪裡重走，讓人決定這一版接不接。
- **層級**：變更（不在主流程上）
- **從哪裡進來**：
  - 專案第一次通過 G1 後進來的變更 CR。
  - 第一次通過 G1 後，外部來源同步發現目前已採用的來源快照和 Jira／Confluence 有內容差異：CR 被修改或取消、spec 頁出了新版本。
  - 第一次通過 G1 後，S 版本同步發現需要範圍或需求決策的變更（例如有人在 repo 裡直接加了新需求）。
  - 重開 G1 或回到 P0／P2 後，又出現尚未經 GC 接受的需求變更。
- **輸入**：變更 CR 或有差異的來源（外部來源同步報告附上的新舊內容）、範圍清單、差異分析、正式紀錄裡的追溯關係。
- **輸出**：
  - 影響報告（`artifacts/changes/<CR 編號>/`）：改到哪個產出物、哪些下游會過期、重新進入點、變更進來的時間點（模組還沒開始／正在跑／已合入整合 branch）。
  - GC 核准接受時：被直接改到的上游產出物新版本（例如追加模組後的差異分析、改版的模組 spec 條目、補上重現 bug 的 case）。來源快照的新版本由工具產生；範圍清單要改時一起改版，差異由 GC 核准，不另外重開 G0。
- **出口檢查**：影響報告完整。
- **出口關卡**：GC 變更核准（這一版接或不接；不接就記錄延後或拒絕）。
- **失敗退回**：影響無法確認 → 交給人。
- **迴圈上限**：待定。
- **可寫範圍**：可寫 `artifacts/changes/<CR 編號>/`；GC 接受後，只能改影響報告列出的上游產出物；不能改來源快照（由工具產生）；禁止改 FW source。
- **人怎麼參與**：與 AI 一起做（討論這一版接不接）。
- **獨立性要求**：無。

變更類型與重新進入點的對照、變更進來的時間點怎麼處理，見 [framework/04 §4.6](../framework/04_rules.md#46-c-變更處理)。

- **執行方式**：影響分析無人在旁執行；GC 討論用互動式 session。
- **工具**：Atlassian MCP、bootcode-qa。
