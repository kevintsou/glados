# v0.9 精簡提案

> **這份文件回答**：GLADOS v0.8.6 哪些關卡、檢查與機制可以拿掉或合併，讓流程回到「加速開發」的本意；拿掉之後會失去什麼、怎麼補；套用要改哪些文件與待辦。
>
> **狀態**：2026-10-19 提出，同日經使用者同意，已套用為 GLADOS v0.9（commit `e655f67`）；套用時的唯一調整見 [CHANGELOG](../CHANGELOG.md) v0.9「套用時的調整」。依使用者同意的三條原則撰寫：機器能便宜驗證、而且真的會出事的才擋；人在場的節點只檢查有沒有交齊；關卡只留真正要人做決定的。另加使用者先前的決定：需要人參與的節點由人自己開 agent 完成，openBCT 只負責開工與收件。

## 1. 為什麼現在太重

v0.8 的設計出發點是「AI 不可信，每一步都要有證據、有版本、有核准，任何上游改動都要自動傳播」。每一條單獨看都有道理，疊起來就變成：

1. **人被叫出來太多次**。專案層 6 個關卡，加上每個模組 H1、H2 與 M1b 討論。E39 如果切成 8 個模組，光模組層就要人出現 24 次，還沒算 GC。
2. **檢查一半在查文件長得對不對**。50 項裡，交接清單格式、檔案 hash 相符、輸入已通過且有效、追溯關係完整、CR 修訂都有歸屬、影響報告完整這類，擋住的都是「文件不合格式」，不是「FW 會壞」。
3. **自動規則的邊界條件比規則本身還長**。最明顯的是需求變更：04 §4.6、§4.7 和 03 §3.2 用了大量篇幅處理「第一次通過 G1 前後」「重開 G1 是否解除管制」「P2b 確認外部修改」「G1 審查包作廢」等情況。這些規則要實作、要測試，人也要讀懂才能操作。
4. **實作被機制綁死**。openBCT 共用待辦 31 張 OBC 任務，大部分在實作這些機制（正式紀錄驗證、狀態推導、R 分類、S 同步、過期傳播、C 處理）。E39 的 P0 要能由 openBCT 跑起來，OBC-010 之前要先做完 12 張任務。
5. **人在場的節點被當成無人在旁處理**。P0b、P3、M1b 這些段落人就在現場，但框架仍要求同樣的交接清單、hash、檢查，等於讓人做完之後再填一次表。

## 2. 精簡原則

| # | 原則 | 意思 |
| :---- | :---- | :---- |
| 1 | 機器擋真風險 | 只有「機器能便宜驗證、而且錯了會造成損失」的才擋關：build、測試、獨立審查、隔離、不可逆動作、交付版本 |
| 2 | 人在場只看交齊 | 人和 agent 一起做的節點，人就是品質把關；openBCT 收件時只確認該交的都在、結構讀得懂，不審內容 |
| 3 | 關卡只留決策 | 人核准的是「做什麼、接不接、能不能交付」這類決定；中間產出不逐份簽 |
| 4 | 自動判定改成提示 | 上游改動、失敗去向、外部來源差異，openBCT 只負責發現並列出可能受影響的地方，由人決定怎麼走 |
| 5 | 每個節點自己的工作方式 | 框架只規定每個節點「交什麼、怎樣算過、誰做」；需要人的節點由人開 agent 完成，openBCT 只開工與收件；無人在旁的節點才由 openBCT 派工 |

v0.8 原本的「只認證據」「球員不兼裁判」「人只守關卡」三條保留，但只用在擋關檢查上，不再延伸到文件格式。

## 3. 新流程總覽

### 3.1 節點

| v0.9 節點 | 做什麼 | 由誰做 | 出口關卡 | 和 v0.8.6 的差別 |
| :---- | :---- | :---- | :---- | :---- |
| P0 專案啟動 | 定範圍、起點、程式碼建立設定、環境 | 外部互動 | G0 | 不再分 P0a／P0b，一個 session 裡 agent 先草擬再問人 |
| P1 基底與基線 | 機械替換、AI 移植、移植審查、量基線 | openBCT 派工 | GB（只在基線有 FAIL 時） | GB 變成有條件 |
| P2 規劃 | 範圍對到 code、切模組、整理 CR、定介面與記憶體預算 | 外部互動 | G1 | 併入原 P3；G1、G2 合併 |
| M1 需求與驗收 | 模組 spec 條目＋驗收合約 | 外部互動 | H（每模組一次） | 原 M2 的驗收合約移到這裡；H1、H2 合併 |
| M2 測試實作 | case、判別能力證明 | openBCT 派工 | — | 只剩測試實作，合約已在 M1 核准 |
| M4 實作 | 計畫＋改 code＋build | openBCT 派工 | — | 併入原 M3；計畫是 M4 內部的工作，不另外審查 |
| M5 驗證 | 跑測試 | openBCT 派工 | — | 不變 |
| M6 獨立審查 | 另一個 session 審 diff | openBCT 派工 | — | 不變 |
| P4 整合 | 合入、端到端 boot flow | openBCT 派工 | — | 不變 |
| P5 全量驗收 | 全部測試、靜態分析、授權掃描、安全審查 | openBCT 派工 | G3 | 不變 |
| P6 交付 | 交出 release | 人 | — | 不變 |
| P7 回寫 | 知識庫、規則、skill 的回寫提案 | 外部互動 | — | 人確認不再算正式關卡，也不擋交付 |
| C 變更 | 新的或改過的 CR 接不接 | 外部互動 | GC | 規則大幅簡化（§5.5） |

節點代號保留原本的（P3、M3、M7 空出來），避免已經在用的文件、工具和討論全部改號。

**外部互動節點怎麼跑**（P0、P2、M1、C、P7）：

1. openBCT 開工：開一個執行編號、準備只含允許內容的工作區與固定輸入、產生工作包（工作區位置、可讀來源、要交的檔案、用哪一版 GLADOS 與 skill）。
2. 人開 agent 完成，openBCT 不參與中間過程。
3. 人提交，openBCT 做收件檢查與該節點的擋關檢查；沒過就把缺什麼交還給人。
4. 有出口關卡的，由核准人送出決定。

**openBCT 派工的節點**（P1、M2、M4、M5、M6、P4、P5）照原本的方式：固定輸入、開新 session、回收、檢查、放行。

### 3.2 人工關卡

| v0.8.6 | v0.9 | 理由 |
| :---- | :---- | :---- |
| G0 啟動核准 | **保留** | 範圍、起點、建立設定是整個專案的根，必須由人決定 |
| GB 基底核准 | **有條件**：基底 build 零警告、基線量完，而且保留的既有功能沒有 FAIL，就自動放行；有 FAIL 才請人逐項決定 | 沒有 FAIL 時人沒有東西要決定 |
| G1 需求基準核准＋G2 架構審查 | **合併成 G1**，P2 規劃結束時一次核准需求整理、模組切分、介面與預算 | P2 和 P3 都是人在場的規劃工作，分兩站兩關卡只增加交接與邊界規則（02 §2.6 整段） |
| H1 需求核准＋H2 驗收合約核准 | **合併成每個模組一次 H**，在 M1 討論結束時核准 spec 與驗收合約 | 「什麼叫做完」和「要做什麼」本來就該一起定；人不用為同一個模組被叫兩次 |
| G3 最終交付核准 | **保留** | mask ROM 交付後不能回頭 |
| GC 變更核准 | **保留** | 範圍變更是決策 |
| P7 人確認 | **取消關卡**，回寫提案由人有空時處理 | 只影響之後的專案，不該擋住這一版 |

所有關卡共同保留的規則：最後一步由人親自送出；AI 不給核准建議；核准綁定核准的人、時間與對象的 commit。拿掉的是「核准綁定每份產出物的版本與內容 hash」「重開時只審差異」這類需要專門機制才做得到的規定。

## 4. 檢查

### 4.1 保留擋關的檢查

| 擋什麼風險 | 檢查 | 節點 | 怎麼做 |
| :---- | :---- | :---- | :---- |
| AI 看到禁看的 branch | 隔離設定正確 | 開工時、每次派工 | 工具 |
| 漏掉 CR | 來源快照完整（張數等於 Epic 總數）；範圍清單涵蓋快照裡每一張 CR | P0 | 工具、自動核對 |
| build 設定被漏掉，功能悄悄消失 | 每個 build 設定都有必要／排除處置 | P0、P1 開始時 | 串接層 checker（OBC-030） |
| P1 生成到一半缺資料 | 建立設定是否齊全（`pending` 為空） | P0 | 格式檢查 |
| 生成區不可再生 | 機械替換可重現 | P1 | 工具重跑比對 |
| 編不過、有 warning | build 零警告（起點與基底、模組、整合都跑） | P1、M4、P4 | 工具 |
| mask ROM 空間爆掉 | 記憶體在預算內 | M4、P4 | 工具 |
| 改壞既有功能卻以為原本就壞 | 既有功能已量測（基線） | P1 | 工具 |
| AI 越界改檔、改到凍結的生成區 | 只寫在允許範圍內 | 所有 openBCT 派工的節點 | git diff |
| 驗收情境漏寫 | 合約的每個必要情境都有 case | M2 | 自動核對 |
| 測試抓不到錯 | 判別能力 | M2 | 工具 |
| AI 放寬測試讓自己過 | 測試沒被動過 | M4 | hash 比對 |
| 功能不對 | 必要 case 全部 PASS | M5、P5 | 工具 |
| 功能、安全錯誤 | 獨立審查沒有未處置的阻擋項目（移植審查、測試落實合約、code 審查、安全審查） | P1、M2、M6、P5 | 另一個 session |
| 整合後開不了機 | 端到端 boot flow 通過 | P4 | 工具 |
| 規則違反、授權風險 | 靜態分析、授權掃描 | P5 | 工具 |
| 全量驗收被縮水 | 測試標準沒被放寬 | P5 | 自動核對 |
| 交錯版本（不可逆） | 交付內容與 G3 核准的版本相符 | P6 | hash 比對 |

另外，不可逆動作（例如 eFuse）一律要人批准，由 hook 擋住，這不是出口檢查但照舊保留。

### 4.2 收件檢查（人在場的節點，只看交齊與結構）

| 節點 | 檢查 |
| :---- | :---- |
| P0 | 四份文件都在；專案設定的必填欄位有值、沒有密碼、token 或本機路徑；影響 build 的環境項目有固定版本；範圍清單每一項都有標記，「移除」與「這版不做」有理由 |
| P2 | 範圍清單裡要做的每一項都對到模組；模組相依沒有循環；記憶體預算總和不超過專案設定的上限；regression 範圍有列 |
| M1 | spec 條目有編號、有來源；沒有未回答的待確認事項；驗收合約每個條目對到 spec 條目 |
| C | 有寫明接或不接；接的話寫明要重做哪些節點 |

收件檢查不審內容好壞，內容由在場的人負責、由關卡核准。

### 4.3 其他檢查的去處

50 項逐項的處置見附錄 A。摘要：

- **由開工或派工方式保證，不另設檢查**：起點版本可取得（取不到就開不了工）、審查者與執行者不同（派工時就開另一個 session）、證據對應目前版本（只拿當前 commit build 出來的 image 去跑測試）、必要核准齊全（openBCT 直接看核准紀錄決定能不能往下）。
- **改成提示**：輸入是最新且已通過、放行前版本檢查。
- **併進其他節點而消失**：計畫涵蓋所有 case、計畫審查（M3 併入 M4，M6 的 code 審查與測試涵蓋）、模組交接齊全（取消 M7）。
- **移除**：交接清單格式正確、檔案 hash 相符、環境就緒（工具用到時失敗就記環境錯誤）、移植修改都有依據（移植審查已涵蓋）、CR 修訂都有歸屬、需求來源已整理、追溯關係完整（只保留 case 引用 spec 條目）、影響報告完整。
- **照跑但不擋交付**：知識庫 eval 不退步（P7 在交付之後）。

## 5. 機制

### 5.1 交接清單與產出物檔頭

| v0.8.6 | v0.9 |
| :---- | :---- |
| 固定格式的 YAML 交接清單：輸入與輸出的編號、版本、hash，自檢、要求的核准、驗證缺口、待確認事項、給下一站、重新進入原因 | 自由格式的**交接說明**（markdown），只要求三段：交了什麼、還沒解決的問題（含驗證缺口與待確認事項）、給下一站的話。輸入與輸出的 commit 由 openBCT 的執行紀錄自動記下 |
| 每份產出物開頭寫 `id`、`version`、`depends_on`（細到條目）、`produced_by` | 不要檔頭。版本靠 git；spec 條目與 case 照舊編號，case 引用 spec 條目編號 |

「下一站光靠交接說明就做得下去」這個要求保留，那是交接的本意。

### 5.2 狀態

- **節點狀態**從 8 種改成 6 種：待開始、進行中、收件檢查中、等人決定（關卡或交給人）、完成、等外部回覆。
- **執行狀態**（準備中、核對中、待同步、中斷待核對等 11 種）是 openBCT 怎麼實作的問題，不寫進框架。
- **產出物不設狀態**。v0.8.6 的「處理狀態＋有效性＋核准狀態」三組，改成直接看：最新 commit 上的檢查結果，以及核准紀錄綁的 commit。

### 5.3 上游改了：從「自動過期」改成「影響提示」

| v0.8.6 | v0.9 |
| :---- | :---- |
| 依條目追溯，上游出新版就自動把相連的下游標為過期，從最早過期的那一站重走 | openBCT 記下每次執行讀了哪些檔案；某個檔案改了，就列出「這些節點用過它」，由人決定重跑哪幾站 |
| 驗證證據綁 image、測試集合、驗證環境的 hash，任一改變就過期 | **保留一條**：image 變了，用舊 image 跑出來的測試結果不算，要重跑。這條便宜、客觀，而且是交付前最後的安全網 |
| 環境清單改版要回 P0 重開 G0 | 只有**影響 build 的項目**（toolchain、生成工具）要固定版本，改了就重 build；skill、MCP、知識庫只記下每次用了哪一版，更新不必重開 G0 |

最後一列也順帶解決 P0 待展開議題「知識庫怎麼真的鎖在環境清單的版本」：知識庫不再需要鎖，只需要記錄。

### 5.4 失敗處理：從「R 規則表」改成「節點內重試＋交給人」

| v0.8.6 | v0.9 |
| :---- | :---- |
| R 失敗分類：11 種失敗類型、各自退回的節點、規則判不出時另派一次獨立分析、每次留 R 判定紀錄 | openBCT 派工的節點在節點內重試，例如 build 不過、測試沒過就重做，最多 3 輪；其他情況一律交給人，附上失敗摘要與證據，由人指定回哪一站 |
| 迴圈上限依節點分 2 輪、3 輪、不設、不適用四類，另有「連續 3 輪同樣失敗」 | openBCT 派工的節點一律 3 輪；人在場的節點不設 |

保留一條硬規則：實作的 AI 不能改測試或驗收合約，由「測試沒被動過」這項檢查擋住。

### 5.5 需求變更：從「G1 分界＋外部同步規則」改成一條規則

v0.9 只用一條規則：**G1 核准之前，CR 的新增、修改、取消都在 P0 或 P2 的討論裡處理；G1 核准之後，一律進變更清單，由人在 GC 決定接不接，接了就由人指定從哪一站重做（agent 可以提供影響建議）。**

拿掉的有：P2b 確認外部修改、CR 修訂紀錄的五種類型、G1 審查包遇到新差異作廢、重開 G1 是否解除變更管制、GC 之後的來源快照逐項核准依據等。外部來源同步改成定期比對、列出差異，交給人決定進 P0／P2 還是 GC，不自動分流。

### 5.6 S 版本同步

| v0.8.6 | v0.9 |
| :---- | :---- |
| 派工前、放行前、偵測到新 commit 時都要比對；6 種變更分類；保留版本同步報告 | openBCT 顯示追蹤中 branch 的新 commit，以及它碰到的檔案被哪些節點用過（同 §5.3 的影響提示）。執行期間輸入被改了，結果仍保留，但標示出來由人決定要不要重跑 |
| 人工直接 commit 要登記 diff、對應模組與需求、判斷影響 | 人工 commit 照樣可以，只要該模組重新 build 與跑測試；不另外登記 |

保留：**不默默覆蓋、reset、merge 或 rebase 人的修改**，遇到衝突一律停下來交給人。

### 5.7 正式紀錄與寫入權限

v0.8.6 要求受保護的紀錄 branch、只有串接層服務帳號能寫，所以 openBCT 要先做好服務帳號與權限。v0.9 改成：紀錄寫在專案工作 branch 與 openBCT 的資料庫，核准紀錄記下核准的人與時間；等到多人、多機同時使用時，再加權限保護。

## 6. 會失去什麼，怎麼補

| 拿掉的東西 | 風險 | 補救 |
| :---- | :---- | :---- |
| 依條目追溯的自動過期 | 改了 spec 的某一條，人可能漏掉要重跑的下游 | openBCT 的影響提示列出用過該檔案的節點；P5 全量驗收是交付前的安全網 |
| R 自動判定退回哪一站 | 非 build、測試類的失敗都要人判斷，人被叫的次數可能變多 | 常見的失敗（code 錯、build 錯）在節點內重試就解決；實際跑 E39 後再看哪幾類值得自動化 |
| M3 計畫的獨立審查 | 計畫有問題時，要到 M6 審 code 或 M5 測試失敗才發現，浪費實作輪數 | M4 最多 3 輪；超過就交給人 |
| H1、H2 分開核准 | 驗收合約和 spec 同一場核准，人可能沒仔細看合約 | M1 的收件檢查要求合約每一條都對到 spec 條目；之後要放寬合約仍須人核准 |
| G1 前後的細緻變更規則 | 邊界情況（例如 G1 核准時剛好有人改 CR）由人判斷，不由規則判斷 | 規則簡單到人一定看得懂；變更清單保留完整紀錄 |
| 受保護的紀錄 branch | 單機時紀錄有可能被改 | 目前只有單一團隊使用；多人使用前再加 |
| 每份產出物的版本與 hash | 事後追查「當時看的是哪一版」要靠 git log | 執行紀錄和核准紀錄都綁 commit，git 能查到任何一版 |

v0.8 的五個設計目標，精簡後的狀態：

- **可驗證**：保留，擋關檢查集中在真正能客觀判斷的項目。
- **可替換**：保留，任何節點仍可換 agent、模型或人。
- **可累積**：保留，P7 仍然回寫，只是不擋交付。
- **可追溯**：降到「case 引用 spec 條目、核准與執行綁 commit」，不再逐條目追溯。
- **可重入**：從自動判定改成人決定。
