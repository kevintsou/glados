# v0.10 提案：AI 工作由人觸發，openBCT 只執行確定性的工具

> **這份文件回答**：v0.9 把「派工」定成「串接層派工給 AI 或工具，人不參與」。這份提案要改成：openBCT 不再派工給 AI，AI 的工作一律由人開 agent、照 skill 執行；openBCT 只開工、收件，自己只跑確定性的工具。文件說明改了之後會失去什麼、怎麼補，以及要改哪些文件與待辦。
>
> **狀態**：2026-10-20 提出，同日經使用者同意（第 8 節的 7 項全部照建議），已套用為 GLADOS v0.10。依 2026-10-20 和使用者的討論整理。使用者的看法：AI 節點不需要由 openBCT 派工，和其他人機節點一樣，由人在 Claude Code 等 agent 觸發 skills 執行，甚至更好；3 輪上限可以寫在 skill 裡。

---

## 0. 一頁摘要

- **openBCT 不派工給 AI**。M2、M4、M6、P1 的移植與移植審查、P5 的安全審查，都改成和 P0、P2、M1、C、P7 一樣：openBCT 開工（工作區、固定輸入、工作包），人開 agent 照 skill 做，做完提交，openBCT 收件。
- **確定性的工具步驟仍由 openBCT 執行**：P1 的起點檢查、機械替換、量基線；M2 的判別能力執行；M4 的正式 build；M5、P4、P5 的測試執行。可以由人按鈕觸發，也可以在前一步通過後自動接續。這些步驟要固定版本、由串接層自己算 hash、借還設備，交給 agent 就證明不了。
- **3 輪上限寫進 skill**。skill 在同一次執行裡自己「修 → 檢查 → 再修」，最多 3 輪，還是沒過就停下來交給人。跨節點的累計（M5 FAIL、M6 阻擋回 M4）由 openBCT 從紀錄算，寫進工作包給 skill 讀。超過上限，openBCT 只提示、不擋。
- **agent 可以自己提交**。提交只觸發收件與擋關檢查，不是核准；核准仍然只能由人在系統確認框完成。
- **無人值守的平行**：主要靠人在下班前開好多個 agent session。定時任務只用在額度恢復後接續與早上彙整；要用定時任務直接開新工作，先確認合規。
- **審查的獨立性**：審查是另一次開工。交接說明記下 session 與模型，收件時核對和實作那次不同。
- **已經做好的不浪費**：A 批的派工骨架拿來跑工具步驟。AI 執行端的命令組裝先保留不用，以後需要「批次模式」再接上。B 批改寫成「這些節點的開工與收件，加上對應的 skills」。

## 1. 為什麼改

v0.9 已經把需要人討論的節點交給人自己開 agent 做。剩下的 AI 節點如果還要 openBCT 派工，openBCT 就得做一整套無人值守的 AI 執行環境：

| 要做的事 | 難在哪裡 |
| :---- | :---- |
| 設定隔離 | `claude -p` 模式下設定檔格式錯誤會被默默忽略，hook 也跟著消失（impl/ai_node_execution） |
| 權限詢問 | 沒人在旁時只能一律拒絕，AI 容易卡住或空轉 |
| timeout、取消、重啟 | 執行端停不停得下來、重啟後怎麼核對，都要另外處理（A 批已經為工具步驟做了一套） |
| 帳號與合規 | 用企業席位做無人值守的自動化，要先問管理員（2026-10-20 決定 1） |
| 判讀 AI 有沒有做完 | AI 回答說「完成」不算數，還是要靠檔案與擋關檢查 |

改由人觸發之後，這些幾乎都不用做。品質本來就不是靠「誰來跑」保證，而是靠收件檢查、擋關檢查與關卡（v0.9 的原則）。人看得到過程、可以隨時導正，也能自由選 Claude Code、Codex 或 desktop。

---

## 2. 原則

1. **openBCT 不派工給 AI**：AI 的工作一律由人開 agent、照 skill 執行。openBCT 只開工、收件，留下正式紀錄。
2. **確定性的工具步驟由 openBCT 執行**：需要固定版本、自己算 hash、借還設備的步驟，由 openBCT 執行，可以由人觸發，也可以自動接續。
3. **規則寫在 skill 與檢查裡，計數與證據留在 openBCT 的紀錄**：skill 管「怎麼做、做幾輪」，openBCT 管「做了什麼、過了沒」。

## 3. 新的執行方式

執行方式改成**以步驟為單位**：一個節點可以同時有「人＋agent」的步驟和「工具」的步驟。節點狀態仍然只有六種（framework/04 §4.3）。

| 節點 | 步驟 | v0.9 | v0.10 |
| :---- | :---- | :---- | :---- |
| P0、P2、M1、C、P7 | 全部 | 外部互動 | 不變：人＋agent |
| P1 | 1 起點檢查（build、build 設定核對） | 派工（工具） | 工具 |
| P1 | 2 機械替換 | 派工（工具） | 工具（A 批已做） |
| P1 | 3 移植 | 派工（AI） | 人＋agent（移植 skill） |
| P1 | 4 移植審查 | 派工（AI，另一個 session） | 人＋agent，另一次開工（審查 skill） |
| P1 | 5 量基線（build、跑既有功能） | 派工（工具） | 工具 |
| M2 | 寫 case；測試審查 | 派工（AI） | 人＋agent；寫和審是兩次開工 |
| M2 | 判別能力（在目前的 image 上跑 case，證明抓得到錯） | 派工（工具） | 工具 |
| M4 | 規劃與實作（agent 自己 build、修的循環） | 派工（AI） | 人＋agent（實作 skill） |
| M4 | 正式 build 證據（build 零警告） | 派工（工具） | 工具，提交後跑 |
| M5 | 上機跑 case | 派工（工具＋AI 判讀 log） | 工具；需要判讀時，由人開 agent（通常併入下一次 M4） |
| M6 | 獨立審查 | 派工（AI） | 人＋agent，另一次開工（審查 skill） |
| P4 | 合入、build、端到端 | 派工（工具＋AI 判讀） | 工具；判讀交給人 |
| P5 | 全量驗收執行 | 派工（工具） | 工具 |
| P5 | 安全審查 | 派工（AI） | 人＋agent（安全審查 skill） |
| P6 與各關卡 | | 人 | 不變 |

**紀錄**：人＋agent 的步驟寫成 `mode: external` 的執行紀錄，照外部互動節點的事件記；工具步驟寫成 `mode: dispatch`，照派工節點每輪一筆記（framework/03 §3.6，不用改格式）。

## 4. 機制

### 4.1 輪數上限搬進 skill

- skill 在同一次執行裡自己循環，最多 3 輪：例如實作 skill 是「改 code → 自己 build、自己檢查 → 修」，移植 skill 也一樣。第 3 輪還沒過就停下來，寫交接說明（每一輪失敗在哪、證據、目前卡住的原因），標「交給人」。
- **跨節點的累計由 openBCT 提供**：M5 必要 case FAIL、M6 有阻擋項目回 M4，都要計入 M4 的輪數（framework/04 §4.5）。只有 openBCT 從紀錄算得出來，所以開工時把「這是第幾輪、前幾輪的失敗證據」寫進工作包，skill 讀了照規定決定繼續或交給人。
- **openBCT 只提示、不擋**：超過 3 輪的提交照樣收件與檢查，畫面顯示「已超過 3 輪」。品質由擋關檢查保證；「測試沒被動過」繼續擋住實作 AI 改測試。
- 人收到「交給人」之後的決定，照現有的決定紀錄（自己來、回哪一站、修環境重跑、再試一次、這版不做）。

### 4.2 agent 可以自己提交

- 現行規格寫的是「人送出提交」（framework/04 §4.2）。改成人或 agent 都可以提交（`POST .../submit` 或提交指令）。
- 提交只觸發收件與擋關檢查，不是核准。核准仍然只能由人在服務跳出的系統確認框完成，AI 拿不到（impl/gate_signoff）。
- agent 能提交、也看得到檢查結果，就能自己循環「沒過 → 修 → 再提交」，不用等人。

### 4.3 工具步驟自動接續

- 專案設定加一個開關：前一步通過後，自動執行下一個工具步驟。例如 M4 提交通過，就自動跑正式 build 和 M5（設備可用時）；P1 第 1 步通過，就接第 2 步。
- 工具步驟不需要 AI，也不牽涉帳號合規。晚上 M4 做完，早上看到的就是「實作＋build＋測試」的結果。
- 設備被占用、環境有問題時，工具步驟停下來交給人，不算輪數（沿用 A 批的骨架）。

### 4.4 審查的獨立性

- M2 的測試審查、M6、P1 的移植審查、P5 的安全審查，都是另一次開工、另一份工作包，和被審的那次分開。
- 審查 skill 在交接說明記下 session 編號與模型；收件檢查核對它和被審那次的 session 不同。模型最好也不同，不同時提示。
- 這是自我申報，但兩邊都有紀錄可查。審查的發現照樣寫成 `glados.finding/v2`，阻擋與否由類型決定（framework/04 §4.8），審查的 AI 不能自己改。

### 4.5 無人值守的平行

| 做法 | 用在哪裡 | 注意 |
| :---- | :---- | :---- |
| 下班前，由人開好多個 agent session | 主要做法：每個可以平行的模組一個 session，各自讀工作包整晚跑 | session 用不會停下來問的權限模式；電腦不能睡；工作區隔離與提交時的「只寫在允許範圍內」把關 |
| 工作包寫明能不能平行 | 哪些模組可以同時開 | openBCT 依 framework/02 §2.6 判斷（A 批已會判斷與顯示），寫進工作包，人照著開就不會撞檔案 |
| 定時任務 | 額度恢復後叫停下的 session 接續；早上彙整各模組結果 | 用定時任務**直接開新工作**等於無人值守自動化，先向管理員確認合規 |
| 工具步驟自動接續 | 4.3 | 不牽涉合規 |

### 4.6 工作包要多帶的東西

這些 AI 步驟的工作包，比現在的外部互動節點多三項：

- 建議用的 skill。
- 輪數與前幾輪的失敗證據（4.1）。
- 能不能和其他模組平行（4.5）。

可寫範圍照各節點卡。

## 5. 會失去什麼，怎麼補

| 失去的 | 怎麼補 |
| :---- | :---- |
| 沒有人觸發就自己開始的工作 | 下班前人觸發加上工具步驟自動接續。剩下完全無人觸發的情況，正好是合規最有疑慮的部分，不做 |
| openBCT 對 AI 權限的強制限制（工具清單、MCP、可寫路徑） | 工作區只含允許的 branch（OBC-008）；提交時檢查「只寫在允許範圍內」；skill 寫明可寫範圍 |
| 由 openBCT 保證「審查是另一個 session、另一個模型」 | 4.4 的自我申報加收件核對，紀錄可查 |
| 輪數由 openBCT 強制 | skill 自律加 openBCT 提示；品質由擋關檢查保證 |
| AI 判讀 M5、P4 的 log | 工具只給 PASS／FAIL 與 log；需要判讀時由人開 agent，通常併入下一次 M4 |
