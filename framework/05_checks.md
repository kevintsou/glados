# 05 檢查：怎樣才算通過

> **這份文件回答**：串接層憑什麼判定一站合格、每個檢查驗什麼、由誰執行、結果怎麼記。
>
> 節點卡的「出口檢查」只列檢查名稱，意思都定義在這裡。

---

## 5.1 只認證據

這是整個框架最核心的規則，也是「節點實作可以替換」的前提：串接層不需要理解節點內部怎麼做，只核對「該做的檢查有沒有做、結果是什麼、有沒有對應到目前的版本」。

- **節點交出的東西都只是「申請」**：交接清單、產出物裡寫的狀態、放在 branch 上的核准檔，都不算數。
- **出口條件由檢查判定**，每個檢查留下一筆證據紀錄（[03 §3.8](03_artifacts.md#38-證據紀錄)）。
- **節點自己跑的結果只供參考**。例如 M4 在 session 裡自己 build 了好幾次，這些 log 可以附在交接清單供參考，但放行看的是串接層派工的那次 build。
- **證據必須對應目前的版本**：受檢對象的版本與 hash、輸入的 commit，以及（如果適用）image、測試集合、驗證環境的 hash。對不上就不算。
- **檢查的意思由框架定，用什麼工具做由實作定**。例如跑 case 現在用 openBCT，以後換別的測試框架，只要留下同樣格式的證據紀錄，框架不用改。

## 5.2 誰來執行檢查

| 執行方式 | 誰做 | 留下什麼 | 步驟 2（人扮演串接層）時怎麼做 |
| :---- | :---- | :---- | :---- |
| 串接層自行核對 | 串接層自己計算，不需要執行環境（例如核對 hash、核對改了哪些檔案） | 證據紀錄 | 人照清單核對，記成證據紀錄 |
| 工具執行 | 串接層派工，用固定的輸入版本在執行環境跑（例如 build、跑 case） | 證據紀錄，附原始 log 或報告與其 hash | 人執行工具，附原始 log 與 hash |
| 獨立審查 | 和被審節點不同的執行者（另一個 session，最好換模型） | 審查發現紀錄＋證據紀錄 | 人開另一個 session 執行 |
| 人工核准 | 有權限的人 | 核准紀錄 | 同左 |

## 5.3 結果值

| 結果 | 意思 | 算通過嗎 |
| :---- | :---- | :---- |
| PASS | 檢查做了，而且符合要求 | 算 |
| FAIL | 檢查做了，行為不符合要求 | 不算，交給 R 失敗分類 |
| 未執行 | 還沒跑，或被跳過 | 不算 |
| 環境錯誤 | 平台、工具或連線出問題，沒有得到有效結果 | 不算，也不能當成行為 FAIL；交給人處理環境 |
| 驗證缺口 | 目前的平台觸發不了或觀察不到 | 不算；登記缺口，由人決定補哪種驗證手段 |

例子：連不上 FPGA、image 下載失敗，記「環境錯誤」，**不能當作成功重現了目標 bug**。

## 5.4 每個節點都要做的共通檢查

這五個檢查讓任何執行者（Claude Code、Codex、人、script）都能接手任何節點：不管誰做，串接層在節點邊界都做同樣的核對。agent 內部的 hook 只是提早攔截的輔助，不能代替這些檢查。

| 檢查 | 驗什麼 | 執行方式 |
| :---- | :---- | :---- |
| 交接清單格式正確 | 交接清單符合 [03 §3.5](03_artifacts.md#35-交接清單) 的格式，必要欄位齊全 | 串接層自行核對 |
| 輸入是最新且已通過 | 交接清單列的輸入（從 R、C 或交給人回來時，也包括退回原因），和派工時固定的一致，而且都「已通過」且「有效」 | 串接層自行核對 |
| 檔案 hash 相符 | 交接清單列的每個產出物，實際內容 hash 和清單一致 | 串接層自行核對 |
| 只寫在允許範圍內 | git diff 只改到節點卡「可寫範圍」允許的路徑（排除專案設定列的「被 git 追蹤的編譯產物」） | 串接層自行核對 |
| 放行前版本檢查 | S 版本同步的放行前檢查沒有未解決的衝突，輸入在執行期間沒有被改（[04 §4.7](04_rules.md#47-s-版本同步)） | 串接層自行核對 |

## 5.5 各節點的檢查

「用到的節點」一欄是索引；每個節點實際要做哪些檢查，以節點卡為準。

### 串接層自行核對（讀文件內容與紀錄就能判斷）

| 檢查 | 驗什麼 | 用到的節點 |
| :---- | :---- | :---- |
| 專案設定完整 | [07 專案設定](07_project_profile.md) 的必填欄位都有填；沒有寫入密碼、token 或機器本機路徑 | P0 |
| 起點版本可取得 | 起點 branch／commit 在工作區裡取得到 | P0 |
| 來源快照完整 | 快照的 CR 張數等於查詢 Epic 回傳的總數；專案設定列的每個 spec 頁都在快照裡；每一項都有內容 hash，Confluence 頁另有版本號（[03 §3.2](03_artifacts.md#32-編號版本與-hash)） | P0 |
| 範圍清單完整 | 來源快照裡的每一張 CR 都在範圍清單裡；每一項都標成新增、修改、保留、移除或這版不做，並引用來源快照的項目；「移除」與「這版不做」附理由。既有功能有沒有盤點齊全，這個檢查判斷不了，由 G0 審閱把關 | P0 |
| 環境清單版本已固定 | 環境清單的每一項（skill、MCP、工具、toolchain、知識庫）都有固定的版本，例如 commit SHA 或版本號；並標明類別（影響 build、影響驗證、只影響 AI） | P0 |
| 範圍清單都有歸屬 | 範圍清單裡標成新增、修改、移除的每一項，都對到一個以上的模組 | P2 |
| CR 修訂都有歸屬 | CR 修訂紀錄的每一項都寫明類型（拆分、補 CR、澄清、修改、外部修改）、對應到範圍清單裡已有的項目、附理由（GLADOS 提出的修訂另附 code 上的證據），並有 P2b 的確認結果；沒有任何一項新增或拿掉範圍清單的項目 | P2 |
| 需求來源已整理 | G1 審核前已做外部來源同步，沒有未整理的來源差異；G0 之後採用的外部修改都記在 CR 修訂紀錄並經 P2b 確認；P2 使用的來源快照和 CR 修訂紀錄版本與分析引用一致，修訂的寫回狀態已確認（設定不寫回時明記只存內部）；第一次通過 G1 後重跑 P2，只採用 GC 已接受的需求變更 | P2 |
| 模組順序已定 | 模組之間的相依沒有循環，有執行順序；改到的檔案有重疊、或要用到另一個模組實作結果的模組，都標為序列（[02 §2.6](02_workflow.md#26-模組之間)） | P2 |
| regression 範圍已定 | 列出受影響的既有功能，以及對應的測試範圍 | P2 |
| 模組介面與預算已定 | 每個模組的對外介面都有編號條目；記憶體預算有分配，總和不超過專案設定的上限 | P3 |
| spec 條目有編號且有來源 | 每一條都有編號、版本，並引用來源（CR、spec 頁、CR 修訂紀錄、知識庫）；沒有整段敘述 | M1 |
| 沒有未解決的待確認事項 | 待確認事項清單是空的，或都已有答案 | M1 |
| 每個必要情境都有 case | 驗收合約列的每個必要條目與情境（好、壞、邊界），都至少有一個 case | M2 |

| 追溯關係完整 | case 引用 spec 條目、計畫步驟引用 case、commit message 引用計畫步驟，都齊全且對到目前版本 | M4、M7 |

| 證據對應目前版本 | 驗證證據綁定的 image、測試集合、驗證環境、驗收合約版本，都和目前一致；image 必須是由目前的 commit build 出來的那一個 | P1、M5、M7、P4、P5 |
| 審查沒有未處置的阻擋項目 | 審查發現紀錄中，阻擋項目都已處置並經獨立審查確認；審查綁定目前的計畫或 diff 的 hash | M3、M6、P5 |

## 5.6 新增或修改檢查

- 新增檢查、或改變既有檢查的意思，就是改框架：要更新這份文件，以及用到它的節點卡，並記在版本紀錄。
- 換掉執行檢查的工具，就是改實作：更新節點卡的實作段即可，只要證據紀錄的格式不變。
- 檢查名稱確認後，轉成機器可讀格式時再配固定的代號；文件裡一律用中文名稱。
