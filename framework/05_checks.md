# 05 檢查：怎樣才算通過

> **這份文件回答**：哪些檢查會擋住往下走、人在場的節點收件時看什麼、每個檢查由誰執行、結果怎麼記。
>
> 節點卡只列檢查名稱，意思都定義在這裡。v0.9 起只有錯了會真的出事的檢查才擋關；原本 50 項檢查逐項的去處見 [v0.9 精簡提案附錄 A](../notes/v0.9_simplification_proposal.md#附錄-a50-項檢查逐項處置)。

---

## 5.1 只認證據

擋關檢查以串接層執行或派工留下的證據為準：

- **節點自己跑的結果只供參考**。例如 M4 在 session 裡自己 build 了好幾次，這些 log 可以寫進交接說明，但放行看的是串接層派工的那次 build。
- **證據綁定 commit**：受檢的 commit，以及（用到時）image hash 與測試基準。對不上就不算。
- **檢查的意思由框架定，用什麼工具做由實作定**。例如跑 case 現在用 openBCT，以後換別的測試框架，只要留下同樣的證據紀錄，框架不用改。

---

## 5.2 誰來執行檢查

| 執行方式 | 誰做 | 留下什麼 | 步驟 2（人扮演串接層）時怎麼做 |
| :---- | :---- | :---- | :---- |
| 自動核對 | 串接層讀檔案與 git 就能判斷（例如核對範圍清單涵蓋每張 CR、git diff 有沒有越界） | 證據紀錄 | 人照清單核對 |
| 工具執行 | 串接層用固定的輸入 commit 在執行環境跑（例如 build、跑 case） | 證據紀錄，附原始 log 或報告 | 人執行工具，留下原始 log |
| 獨立審查 | 和被審者不同的執行者（另一個 session，最好換模型） | 審查發現紀錄＋證據紀錄 | 人開另一個 session 執行 |

---

## 5.3 結果值

| 結果 | 意思 | 算通過嗎 |
| :---- | :---- | :---- |
| PASS | 檢查做了，而且符合要求 | 算 |
| FAIL | 檢查做了，行為不符合要求 | 不算 |
| 未執行 | 還沒跑，或被跳過 | 不算 |
| 環境錯誤 | 平台、工具或連線出問題，沒有得到有效結果 | 不算，也不能當成行為 FAIL；交給人處理環境 |
| 驗證缺口 | 目前的平台觸發不了或觀察不到 | 不算；登記缺口，由人決定補哪種驗證手段 |

例子：連不上 FPGA、image 下載失敗，記「環境錯誤」，**不能當作成功重現了目標 bug**。

## 5.4 擋關檢查

沒過就不能往下走。每一項都對應一個錯了會真的出事的風險。

| 檢查 | 擋住什麼風險 | 驗什麼 | 節點 | 執行方式 |
| :---- | :---- | :---- | :---- | :---- |
| 隔離設定正確 | AI 看到禁看的 branch | 工作區 repo 只含允許的 branch；agent 的 GitLab 權限只限這個 repo | 開工時、每次派工 | 工具 |
| 來源快照完整 | 漏抓 CR | 快照的 CR 張數等於查詢 Epic 回傳的總數；專案設定列的每個 spec 頁都在；程式碼建立設定列的每個外部來源都有快照與版本 | P0 | 工具 |
| 範圍清單涵蓋所有 CR | 漏掉 CR | 來源快照裡的每一張 CR 都在範圍清單裡 | P0 | 自動核對 |
| build 設定都有處置 | build 設定被漏掉，功能悄悄消失 | 起點盤點出的每個 build 設定，在專案設定裡都列為必要，或附理由與範圍依據明確排除；沒有待確認 | P0、P1 開始時 | 自動核對（串接層 checker） |
| 建立設定是否齊全 | P1 生成到一半缺資料 | 有程式碼建立設定時，建立設定的必填欄位齊全、`pending` 是空的、移植範圍沒有落在生成區（[impl/recipe](../impl/recipe.md)） | P0 | 自動核對 |
| 機械替換可重現 | 生成區不可再生 | 用同一份程式碼建立設定、同一版工具和外部來源快照重跑，產出和機械替換 commit 逐檔相同；只寫在生成區與起始複製區 | P1 | 工具 |
| build 零警告 | 編不過、有 warning | 專案設定列的每一個必要 build 設定都實際 build 成功、0 warning；記錄每個設定的 image hash。起點、基底、模組、整合都要跑；核准的排除項目不計為 PASS | P1、M4、P4 | 工具 |
| 記憶體在預算內 | mask ROM 空間爆掉 | ROM、SRAM、stack 用量在 P2 分配的預算與專案設定的上限內 | M4、P4 | 工具 |
| 既有功能已量測 | 改壞既有功能卻以為原本就壞 | 基底 image 上，範圍清單列的既有功能都有執行結果；保留的既有功能 FAIL 時列進基線待處理清單，交 GB 處置 | P1 | 工具 |
| 只寫在允許範圍內 | AI 越界改檔、改到凍結的生成區 | git diff 只改到節點卡「可寫範圍」允許的路徑（排除專案設定列的「被 git 追蹤的編譯產物」） | 所有派工節點 | 自動核對 |
| 每個必要情境都有 case | 驗收情境漏寫 | 驗收合約列的每個必要條目與情境（好、壞、邊界），都至少有一個 case | M2 | 自動核對 |
| 判別能力 | 測試抓不到錯 | 證明 case 真的抓得到問題（三種證明方式見 [nodes/M2](../nodes/M2.md)） | M2 | 工具 |
| 測試沒被動過 | AI 放寬測試讓自己過 | 驗收合約與測試實作的內容 hash 和測試基準一致 | M4 | 自動核對 |
| 必要 case 全部 PASS | 功能不對 | 在指定的驗證環境，對當前 commit build 出來的 image 跑測試，驗收合約列的必要 case 全部有跑而且全部 PASS；未執行、跳過、環境錯誤都不算 | M5、P5 | 工具 |
| 審查沒有未處置的阻擋項目 | 功能或安全錯誤 | 獨立審查的發現中，阻擋項目都已處置（[04 §4.8](04_rules.md#48-審查放行)）。包括 P1 移植審查（有依據、沒越界、沒關掉功能或放寬設定）、M2 測試審查（case 真的落實合約）、M6 code 審查、P5 安全審查 | P1、M2、M6、P5 | 獨立審查 |
| 端到端 boot flow 通過 | 整合後開不了機 | 整合後的 image 整條 boot flow 都通過 | P4 | 工具 |
| 靜態分析 | 違反必要規則 | 依專案設定的必要規則清單跑靜態分析，沒有未處置的必要項目 | P5 | 工具 |
| 授權掃描 | 授權或漏洞風險 | 授權與漏洞掃描沒有未處置的風險 | P5 | 工具 |
| 測試標準沒被放寬 | 全量驗收被縮水 | 使用的測試集合是各模組最新的測試基準；沒有被移除或放寬。只有範圍清單標成「移除」的功能，它的 case 可以拿掉 | P5 | 自動核對 |
| 交付內容與核准版本相符 | 交錯版本（不可逆） | release 包裡的 image hash，和 G3 核准時的一致 | P6 | 自動核對 |

另外，**不可逆動作**（例如 eFuse 燒錄）一律要人批准，由 hook 擋住；這不是出口檢查，但全程有效。

## 5.5 收件檢查

外部互動節點提交時，串接層只看交齊與結構，不審內容好壞；內容由在場的人負責、由關卡核准。

| 節點 | 收件檢查 |
| :---- | :---- |
| P0 | project.md、scope.md、profile.json、environment.json 都在；專案設定的必填欄位有值，沒有密碼、token 或本機路徑；影響 build 的環境項目有固定版本；範圍清單每一項都有標記，「移除」與「這版不做」有理由；有交接說明 |
| P2 | 範圍清單裡標成新增、修改、移除的每一項都對到模組；每個模組的 code 範圍列到檔案；模組相依沒有循環；記憶體預算總和不超過專案設定的上限；regression 範圍有列；有交接說明 |
| M1 | spec 條目有編號、每條有來源；沒有未回答的待確認事項；驗收合約每一條對到 spec 條目；有交接說明 |
| C | 寫明接或不接；接的話寫明要改哪些產出物、從哪一站重做；有交接說明 |
| P7 | 回寫提案每一項附上來源紀錄 |

收件檢查沒過，把缺什麼交還給人，不計輪數。

---

## 5.6 新增或修改檢查

- 新增擋關檢查、或改變既有檢查的意思，就是改框架：要更新這份文件與用到它的節點卡，並記在版本紀錄。新增擋關檢查前，先確認它擋的是錯了會真的出事的風險（[01 §1.3](01_overview.md#13-設計原則) 原則 1）。
- 換掉執行檢查的工具，就是改實作：更新節點卡的實作段即可。
- 轉成機器可讀格式時再配固定的代號；文件裡一律用中文名稱。
