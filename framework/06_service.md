# 06 串接層服務的要求

> **這份文件回答**：不論用什麼工具實作，串接層服務都必須做到哪些事。
>
> 串接層「怎麼判斷」見 [04 串接層規則](04_rules.md)；服務用什麼實作、怎麼接 openBCT 見 [impl/service.md](../impl/service.md)。

---

## 6.1 獨立的背景服務

- **服務是獨立程式**，生命週期與 GUI 分開；關閉 GUI、使用者登出，都不會連帶停止服務。
- **開啟 openBCT 的 GLADOS 分頁時先檢查服務**：已啟動就連線，未啟動就自動啟動。也可以不開 openBCT，單獨啟動或停止服務。
- **同一個服務只會有一個實例。**
- **使用者主動停止後**，已開啟的分頁顯示「服務已停止」並提供「啟動服務」按鈕，不能因為持續監控就馬上自動重啟；再次開啟分頁時才重新檢查並按需啟動。背景常駐不代表使用者不能停止它。
- **自動啟動服務不等於授權執行節點**，派工仍然依專案設定與關卡。

## 6.2 統一派工

- **操作入口不實作放行規則**：GUI、CLI、API／MCP 只送要求給服務，由服務依 [04](04_rules.md) 判斷。
- **同一個節點同一時間只放行一次執行**；不同入口不能各自派工。

## 6.3 持久保存與中斷恢復

進度、核准索引、執行紀錄、版本同步分析與中斷狀態都要持久保存。記憶體裡的工作佇列或事件通知不能當唯一的事實來源。

| 情況 | 服務要怎麼做 |
| :---- | :---- |
| 一般停止 | 先停止新派工，顯示「停止中」；正在執行的工作回收並保存結果後才退出，不啟動下一站。等待人工核准的節點保存後即可退出。同步失敗就保存「待同步」狀態，不把還沒同步的結果宣稱為正式完成 |
| 立即停止 | 要求取消執行，保存已取得的產出、log 與中斷狀態。沒能確認停止的執行端或設備，明列為「待核對」，不推定已停止或已釋放 |
| 重新啟動 | 先核對殘留的執行、設備與待同步紀錄，再決定接續或重跑，不盲目重派同一個工作 |

## 6.4 正式紀錄和即時狀態分開

- **正式進度**以已寫入正式紀錄的為準（[03 §3.11](03_artifacts.md#311-存放位置與寫入權限)）。
- **即時狀態**（正在跑、第幾輪、log、設備占用）來自執行端。
- 兩者用專案編號、節點、執行編號、輸入 commit 對齊，不互相覆蓋；任何一邊連不上時要明確標示「無法取得」，不推定。
- 一個節點可以有多次執行；程式正常結束只代表程式跑完，不代表節點完成。

## 6.5 查詢不需要執行環境

- 只看進度不必 clone、不必連設備。
- 要執行時才準備工作區，而且看得到的 branch 必須遵守專案設定的隔離限制。

## 6.6 CI

- **只改 `.glados/`（或只改紀錄 branch）的 commit 不能觸發 FW 的 CI pipeline**，否則每次交接、每份同步報告都會跑一次 build、靜態分析、授權掃描。
- 需要這些檢查時，由串接層在對應節點明確觸發（例如 M4 的 build、P5 的靜態分析與授權掃描）。
- 具體做法依各專案的 CI 設定（例如 pipeline 規則排除只改 `.glados/**` 的 commit、紀錄 branch 不跑 pipeline），寫進專案設定。
