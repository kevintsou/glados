## 1.1 GLADOS 要做到的事

從需求（spec、CR）出發，經過 spec 討論、功能實作、驗證、regression，最後產出一版功能正常、可以使用的 bootcode FW code。過程由 AI agent／skill、MCP、工具、人工審閱分工完成。

流程切成多個**階段**與多個**模組**，每次交接都有固定格式的交接文件與 checklist（類似 design review list），確保每一站的產出合格才往下走。

**適用範圍**：Phison 的 bootcode 專案，包括：

- 不同 CPU 與 toolchain（ARM Cortex-R5／DS-5、Andes RISC-V）。
- 新 IC，或從前代 IC 延伸（delta）的專案。
- mask ROM 或非 ROM 的 boot code。

E39（PS5039）是第一個用來開發與驗收 GLADOS 的專案，見 [projects/E39.md](../projects/E39.md)。

## 1.2 五個設計目標

| 目標 | 意思 | 靠什麼達成 |
| :---- | :---- | :---- |
| 可驗證 | 每一站做完都能客觀判斷合不合格 | 出口條件寫成可執行的檢查；先定驗收再寫 code |
| 可追溯 | 每一行 code 都能追到哪條需求、哪個 case | 產出物編號＋版本＋引用關係 |
| 可重入 | 需求變更或失敗時，只重做受影響的部分 | 過期機制（[03 §3.5](03_rules.md)） |
| 可替換 | 任何節點可以換成別的 agent、模型或人來做 | 節點只靠交接清單溝通；檢查由串接層統一執行 |
| 可累積 | 這次的錯變成下次的能力 | P7 回寫到知識庫、規則、skill、hook |

## 1.3 三層：框架、節點實作、專案

GLADOS 的文件分三層。這一版先把「框架」這層定下來。

| 層 | 內容 | 放在哪裡 | 什麼時候改 |
| :---- | :---- | :---- | :---- |
| **框架** | 流程怎麼走、每個節點的介面（吃什麼、交什麼、怎樣算過、失敗退回哪裡）、交接與紀錄格式、檢查的定義、串接層的規則 | `framework/`，以及 `nodes/` 每張節點卡的「介面」段 | 流程本身要改時才改；對所有專案都一樣 |
| **節點實作** | 誰來執行、用哪個模型與工具、怎麼接 openBCT 或 remote-ice、串接層服務怎麼寫 | `nodes/` 每張節點卡的「實作」段，以及 `impl/` | 換工具、換模型、補能力時改；不影響框架 |
| **專案** | 專案設定、範圍、試點、專案自己的待決事項 | `projects/` | 每個專案一份 |

這三層之間的規則：

1. **框架只規定「要交什麼、怎樣算過、失敗去哪裡」**，不規定「誰做、用什麼工具做」。
2. **節點實作可以替換**：只要交出符合介面的交接清單、通過介面列出的檢查，串接層的規則就不用改。
3. **實作做不到介面的要求時，登記成驗證缺口**，由人決定補哪種手段。不能因為實作不方便，就回頭放寬框架。舉例：M5 驗證如果拿不到「測試當時 FPGA 上是哪個 image」的證明，就登記缺口，不能算通過。
4. **某個專案需要改流程本身，代表框架還不夠通用**，應該回頭修框架，而不是讓那個專案自己改一套。

## 1.4 用語

| 用語 | 意思 |
| :---- | :---- |
| **階段**（P0–P7） | 專案層的節點，每個專案各跑一次 |
| **模組** | 會改到同一塊 code 的一組 CR，例如 lcp、host 介面、安全。由 P2 差異分析切分 |
| **模組流程**（M1–M7） | 每個模組各跑一份的子流程 |
| **範圍 CR** | T0 之前的 CR，是 P2 差異分析的輸入，決定這一版要做什麼 |
| **變更 CR** | T0 之後才進來的 CR，由 C 變更分析處理 |
| **T0** | 範圍 CR 的截止點，在 P0 專案啟動時決定 |
| **產出物** | 每一站交出的檔案（spec、case、計畫、diff、報告…），有編號、版本與內容 hash |
| **交接清單** | 每一站結束時交出的固定格式清單：用了哪些上游產出物、交出哪些產出物、有哪些待決或缺口（[04 §4.3](04_records.md)） |
| **節點卡** | 每一站的規格，分「介面」與「實作」兩段（[nodes/README](../nodes/README.md)） |
| **節點介面** | 節點卡中由框架固定的部分：目的、輸入、輸出、出口檢查、關卡、失敗退回、迴圈上限、可寫範圍、獨立性要求 |
| **節點實作** | 節點卡中可以替換的部分：執行者、模型、工具、執行方式 |
| **檢查** | 出口條件的最小單位。每個檢查有固定名稱、要驗什麼、由誰執行、留下什麼證據（[05 檢查清單](05_checks.md)） |
| **證據紀錄** | 一次檢查執行後留下的紀錄，寫明檢查了哪個版本、用了哪些輸入、結果是什麼 |
| **關卡** | 需要人核准的點：專案層 G0–G3、變更核准 GC、模組層 H1、H2（[02 §2.4](02_workflow.md)） |
| **串接層** | 確定性的流程管理背景服務（不是 LLM），負責觀察進度、版本同步、守門與派工。GUI、CLI、API 都只是它的操作入口 |
| **正式紀錄** | 只有串接層服務能寫入的紀錄：哪些產出物已通過、核准索引、正式進度、版本同步報告（[03 §3.11](03_rules.md)） |
| **S 版本同步** | 開啟專案、偵測到新 commit、每次派工前、每次放行前都會執行的版本比對與影響檢查（[03 §3.8](03_rules.md)） |
| **R 失敗分類** | 模組內部發現問題時，依規則判斷是哪一類失敗、要退回哪一站（[03 §3.6](03_rules.md)） |
| **C 變更分析** | 判斷變更 CR 改到哪個產出物、哪些下游要重做的節點（[nodes/C](../nodes/C.md)） |
| **執行紀錄** | 一個節點的一次嘗試：編號、固定的輸入版本、狀態、log 與結果。一個節點可以有多次嘗試 |
| **GLADOS 專案** | 有專案編號的一份需求範圍與流程實例。同一個 FW repo 可以有多個 GLADOS 專案 |
| **專案設定** | 每個專案接上 GLADOS 時要填的一份設定：toolchain、build、驗證平台、觀察手段、code 模組對照等（[06](06_project_profile.md)） |

## 1.5 設計原則

1. 一個節點只負責一件事，交出一份完整的交接包（可以含多份產出物）。節點之間只靠交接清單溝通，加上進入下一站的條件。
2. 節點有四種執行者：AI（skill／agent）、工具（build、ICE、測試框架等結果固定的）、人、串接層自己。
3. 退回哪一站由規則決定，不由產出者自己決定（球員不兼裁判）。
4. 每個迴圈都有輪數上限，超過就交給人。
5. **重新進入點＝最早一個「輸入產出物出了新版」的節點。** 失敗退回（R）、需求變更（C）與版本同步（S）發現的變更，都透過同一套相依與過期機制決定從哪裡重走。單純的進度紀錄 commit 不會讓 FW 證據失效。
6. **人只守關卡。** 人核准範圍、架構、需求、驗收標準、不可逆動作與最終交付。中間的計畫、diff、報告由 AI 產出、獨立審查、工具驗證，串接層依規則放行，不逐份要求人簽。人工核准和「產出物通過檢查」是兩件事。
7. **框架定介面，實作可以替換**（§1.3）。
8. **只認證據，不認自己說的話。** 出口條件由檢查留下的證據紀錄判定。節點自己寫的「PASS」「已通過」、自己放的核准檔，都不算數（[03 §3.2](03_rules.md)）。

## 1.7 建置路線

| 步驟 | 做什麼 | 完成的判斷 |
| :---- | :---- | :---- |
| 1a. 框架文件 | 流程、所有節點卡的介面、交接與紀錄格式、檢查清單、串接層規則寫成文件（**v0.7 的目標**） | 文件審過，沒有未決的框架問題 |
| 1b. 打底 | 填第一份專案設定；把既有測試項目轉成測試框架 case；不可逆動作用 hook 擋 | 專案設定審過 |
| 2. 手動跑一個模組 | 挑一個邊界清楚的模組，由人扮演串接層，每個節點開獨立 session，手動跑完 M1–M7 | 這個模組產出合格交付，交接清單在每一站都夠用 |
| 3. 接上串接層服務 | 背景服務＋操作入口（openBCT GLADOS 分頁）；開啟 GitLab／本機 repo；`.glados/`；環境檢查、版本同步、持久紀錄、雙來源監控、手動啟動與回收，再接自動派工與 3 輪停止 | 查詢 GitLab 不需 clone；執行時按需準備工作區；人工 commit 可追蹤；一個模組能自動派工跑完，人只出現在關卡 |
| 4. 擴大到整個專案 | 所有模組、P4 整合、P5 全量驗收、C 變更處理 | 交出整版 FW，通過驗收（[projects/E39.md](../projects/E39.md)） |
| 5. 第二個專案 | 換一個專案只填新的專案設定 | 不用改流程就能跑，證明平台是通用的 |

步驟 5 很重要：只在一個專案上跑通，只能證明 GLADOS 適用於那個專案。要證明它是平台，必須在第二個專案上「只換專案設定」也跑得通。

**各機制從哪一步開始需要**

步驟 2 要驗證的是流程與交接規則本身；工具化放到步驟 3，避免流程還沒驗證就先投入大量開發。

| 機制 | 步驟 2（手動跑一個模組） | 步驟 3 起 |
| :---- | :---- | :---- |
| 交接清單、證據綁版本與 hash、判別能力證明、審查發現紀錄 | 必須，這些就是要驗證的流程本身 | 必須 |
| 串接層 | 由人照節點卡與檢查清單扮演 | 背景服務 |
| 檢查的執行 | 串接層自行核對的項目由人照清單核對；需要工具的項目由人執行工具，並把原始 log 與 hash 記成證據紀錄 | 服務自動執行或派工 |
| 版本同步 | 由人在派工前、放行前用 git diff 與 hash 對照清單 | 服務自動執行 |
| 正式紀錄與信任邊界 | 由人在受保護的 branch 提交正式紀錄；核准用 MR approval 或簽章 commit | 只有服務帳號可寫 |
| 隔離與 CI 規則 | 必須（有禁看 branch 的專案從第一天就要隔離） | 必須 |
| GUI、雙來源監控、遠端 worker、自動派工、3 輪自動停止 | 不需要 | 逐步加上 |

## 附錄 A：對 playbook 頁 kit 範本的修正建議

**3\_CLAUDE.md**

- Model Routing、「不准改驗收清單其他欄位」等關鍵約束不應只寫在 CLAUDE.md（playbook 頁心法 6：CLAUDE.md 只是提醒）。模型分工放在節點啟動設定，欄位保護用節點的 PreToolUse hook，並由串接層在節點邊界再檢查一次（[03 §3.13](03_rules.md)）。
- bootcode 通用紅線應寫進平台預設：記憶體預算、linker script 不准動、所有 polling 都要有 timeout、MISRA、不可動態配置記憶體、register 只能經由 HAL 存取。
- 「spec 沒寫的行為不實作」太嚴：timeout、防禦性檢查通常 spec 不會寫，需要一份「預設允許的防禦性行為」清單。
- build 工具依專案設定選擇，不寫死。

**2\_feature\_list.json／5\_regression\_gate.md 的防作弊漏洞**

- passes、evidence 由 agent 自己寫；`REVIEW: APPROVED` 也是寫進 plan.md 的字串，實作 agent 自己就能寫。建議 passes 由測試結果腳本產生；review 結論由另一個 process 寫入獨立檔案並綁定 diff hash。
- regression\_gate.py 沒檢查 report 對應的 image hash，舊的 PASS report 也會被放行。
- block\_irreversible.py 用黑名單 regex，包一層 script 就能繞過；改用白名單。
- 合法新增 case 後，由串接層依已核准驗收合約、獨立審查與工具證據建立新版測試基準。合約變更才回 H2；實作 agent 無權移動（[nodes/M2](../nodes/M2.md)）。
