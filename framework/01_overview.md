## 1.1 目標與範圍

**GLADOS 要做到的事**：從需求（spec、CR）出發，經過需求釐清、驗收定義、實作、驗證、整合與全量驗收，最後產出一版功能正常、可以使用的 bootcode FW code。工作由 AI agent／skill、MCP、工具、人工審閱分工完成；流程切成多個**節點**，每一站都交出固定格式的交接清單（類似 design review list），檢查合格才往下走。

**適用範圍**：Phison 的 bootcode 專案，包括：

- 不同 CPU 與 toolchain（ARM Cortex-R5／DS-5、Andes RISC-V）。
- 新 IC，或從前代 IC 延伸（delta）的專案。
- mask ROM 或非 ROM 的 boot code。

E39（PS5039）是第一個用來開發與驗收 GLADOS 的專案，見 [projects/E39.md](../projects/E39.md)。

**五個設計目標**：

| 目標 | 意思 | 靠什麼達成 |
| :---- | :---- | :---- |
| 可驗證 | 每一站做完都能客觀判斷合不合格 | 出口條件寫成可執行的檢查；先定驗收再寫 code |
| 可追溯 | 每一行 code 都能追到哪條需求、哪個 case | 產出物編號＋版本＋引用關係 |
| 可重入 | 需求變更或失敗時，只重做受影響的部分 | 過期與重新進入的規則 |
| 可替換 | 任何節點可以換成別的 agent、模型或人來做 | 節點只靠交接清單溝通；檢查由串接層統一執行 |
| 可累積 | 這次的錯變成下次的能力 | P7 回寫到知識庫、規則、skill、hook |

## 1.2 核心概念

整套框架只靠六個概念運作。先讀懂這六個，其他文件都是它們的細節。

1. **節點**：流程切成專案層的 P0–P7、每個模組各跑一次的 M1–M7，以及處理變更 CR 的 C。每個節點有一張節點卡，寫明它吃什麼、交什麼、怎樣算過、失敗退回哪裡。→ [02 流程](02_workflow.md)、[nodes/](../nodes/README.md)
2. **產出物與交接清單**：每一站交出產出物（spec、計畫、diff、報告…），加上一份固定格式的交接清單。交接清單只是「申請」，不是結果。→ [03 產出物與紀錄](03_artifacts.md)
3. **檢查與證據**：每一站的出口條件拆成一個個檢查。檢查由串接層執行或派工，留下證據紀錄；**只認證據，不認節點自己說的話**。→ [05 檢查](05_checks.md)
4. **人工關卡**：人的核准只在關卡：範圍、架構、需求、驗收標準、不可逆動作與最終交付。需要討論的決策，在關卡前的互動段落（P0b、P2b、P3 架構審查會議、M1b、C 的討論）由人和 AI 一起定案；中間的計畫、diff、報告不逐份要人簽。→ [02 §2.4 人工關卡](02_workflow.md#24-人工關卡)
5. **串接層**：一個確定性的流程管理者（不是 LLM）。它派工、執行檢查、決定放行或退回，而且是唯一能寫正式紀錄的身分。→ [04 串接層規則](04_rules.md)、[06 串接層服務的要求](06_service.md)
6. **過期與重新進入**：上游產出物出了新版，依賴它的下游就過期，從最早過期的那一站重走。失敗退回（R）、變更 CR（C）、新 commit（S）都走這同一套機制。→ [04 §4.4 過期與重新進入](04_rules.md#44-過期與重新進入)

## 1.3 設計原則

| # | 原則 | 意思 | 落在哪裡 |
| :---- | :---- | :---- | :---- |
| 1 | 一個節點只做一件事 | 交出一份完整的交接包；節點之間只靠交接清單溝通。每個節點都開新的 session，不給前一站的對話，這樣才驗證得出「光靠交接清單就做得下去」 | [04 §4.1](04_rules.md#41-串接層是什麼) |
| 2 | 只認證據 | 出口條件由串接層執行檢查留下的證據判定；節點自己寫的「PASS」「已通過」、自己放的核准檔都不算數 | [05 §5.1](05_checks.md#51-只認證據) |
| 3 | 球員不兼裁判 | 退回哪一站由規則決定，不由產出者自己決定；審查一定由另一個執行者做 | [04 §4.5](04_rules.md#45-r-失敗分類) |
| 4 | 人只守關卡 | 人核准決策；中間產出由檢查與獨立審查放行。人工核准和「通過檢查」是兩件事 | [02 §2.4](02_workflow.md#24-人工關卡) |
| 5 | 同一套過期機制 | 重新進入點＝最早一個「輸入出了新版」的節點；單純的進度紀錄 commit 不會讓 FW 證據失效 | [04 §4.4](04_rules.md#44-過期與重新進入) |
| 6 | 迴圈有上限 | 每個迴圈都有輪數上限，超過就交給人 | [04 §4.9](04_rules.md#49-迴圈上限與交給人) |
| 7 | 框架定介面，實作可替換 | 框架只規定「交什麼、怎樣算過、失敗去哪裡」；Claude Code、Codex、人、script 都能接手任何節點 | §1.4 |
| 8 | 不為實作放寬框架 | 實作做不到介面的要求時，登記成驗證缺口交給人決定；某個專案需要改流程，代表框架不夠通用，要回頭修框架 | §1.4 |

## 1.4 三層：框架、節點實作、專案

GLADOS 的文件分三層。v0.7 先把「框架」這層定下來。

| 層 | 內容 | 放在哪裡 | 什麼時候改 |
| :---- | :---- | :---- | :---- |
| **框架** | 流程、節點介面、產出物與紀錄格式、檢查、串接層規則與服務要求 | `framework/`，以及 `nodes/` 每張卡的「介面」段 | 流程本身要改時才改；對所有專案都一樣 |
| **節點實作** | 誰來執行、用哪個模型與工具、怎麼接 openBCT 或 remote-ice、串接層服務怎麼寫 | `nodes/` 每張卡的「實作」段，以及 `impl/` | 換工具、換模型、補能力時改；不影響框架 |
| **專案** | 專案設定、範圍、試點、專案自己的待決事項 | `projects/` | 每個專案一份 |

三層之間的規則：

1. **框架只規定「要交什麼、怎樣算過、失敗去哪裡」**，不規定「誰做、用什麼工具做」。
2. **節點實作可以替換**：只要交出符合介面的交接清單、通過介面列出的檢查，串接層的規則就不用改。
3. **實作做不到介面的要求時，登記成驗證缺口**，由人決定補哪種手段。例如 M5 驗證拿不到「測試當時 FPGA 上是哪個 image」的證明，就登記缺口，不能算通過。
4. **專案需要改流程本身，就回頭修框架**，不讓那個專案自己改一套。

## 1.5 平台組成

| 組成 | 內容 | 通用或專案專屬 |
| :---- | :---- | :---- |
| 流程定義 | 流程圖、節點卡、檢查、串接層規則 | 通用 |
| 串接層服務 | 背景常駐的流程管理服務；唯一能寫正式紀錄的身分 | 通用 |
| 操作入口 | GUI、CLI、API／MCP，都透過串接層服務操作，本身不實作放行規則。第一個 GUI 入口是 openBCT 的 GLADOS 分頁 | 通用 |
| 共用工具 | skills、MCP、測試框架、審查工具（[impl/tools.md](../impl/tools.md)） | 通用 |
| 專案設定 | toolchain、build、驗證平台、觀察手段、code 模組對照、隔離與 CI 規則…（[07](07_project_profile.md)） | 每個專案一份 |
| 專案工作區與紀錄 | 預設就是 FW repo，GLADOS 資料放 `.glados/`；有隔離限制時改用只含允許 branch 的獨立 repo（[03 §3.11](03_artifacts.md#311-存放位置與寫入權限)） | 每個專案一份 |

換一個專案時，只需要填一份新的專案設定、在專案工作區建立新的 `.glados/` 專案紀錄；流程、串接層服務、工具都不用改。

## 1.6 建置路線

| 步驟 | 做什麼 | 完成的判斷 |
| :---- | :---- | :---- |
| 1a. 框架文件 | 流程、所有節點卡的介面、產出物與紀錄格式、檢查、串接層規則寫成文件（**v0.7 的目標**） | 文件審過，[08](08_open_questions.md) 的框架待決事項都有結論 |
| 1b. 打底 | 填第一份專案設定；把既有測試項目轉成測試框架 case；不可逆動作用 hook 擋 | 專案設定審過 |
| 2. 手動跑一個模組 | 先照專案的完整範圍跑完 P0–P3（經 G0–G2 核准），再挑一個邊界清楚的模組，由人扮演串接層，每個節點開獨立 session，手動跑完 M1–M7 | 這個模組產出合格交付，交接清單在每一站都夠用 |
| 3. 接上串接層服務 | 背景服務＋操作入口（openBCT GLADOS 分頁）；開啟 GitLab／本機 repo 與 `.glados/`；環境檢查、版本同步、持久紀錄、正式紀錄與即時狀態的雙來源監控、手動啟動與回收，再接自動派工與 3 輪停止 | 查詢 GitLab 不需 clone；執行時按需準備工作區；人工 commit 可追蹤；一個模組能自動派工跑完，人只出現在關卡 |
| 4. 擴大到整個專案 | 所有模組、P4 整合、P5 全量驗收、C 變更處理 | 交出整版 FW，通過驗收（[projects/E39.md](../projects/E39.md)） |
| 5. 第二個專案 | 換一個專案只填新的專案設定 | 不用改流程就能跑，證明平台是通用的 |

**步驟 2 的 P0–P3 為什麼要照完整範圍**：如果只整理試點模組的那幾張 CR，第一次通過 G1 之後，其他 CR 全都會變成變更 CR，要一張一張走 C 變更分析與 GC 核准；P3 也會在沒看過其他模組的情況下定介面，之後可能要重做。照完整範圍跑，M1 會晚一點開始，但步驟 4 可以直接沿用。

步驟 5 很重要：只在一個專案上跑通，只能證明 GLADOS 適用於那個專案；在第二個專案上「只換專案設定」也跑得通，才證明它是平台。

**各機制從哪一步開始需要**：步驟 2 要驗證的是流程與交接規則本身，工具化放到步驟 3，避免流程還沒驗證就先投入大量開發。

| 機制 | 步驟 2（手動跑一個模組） | 步驟 3 起 |
| :---- | :---- | :---- |
| 交接清單、證據綁版本與 hash、判別能力證明、審查發現紀錄 | 必須，這些就是要驗證的流程本身 | 必須 |
| 串接層 | 由人照節點卡與檢查扮演 | 串接層服務 |
| 檢查的執行 | 自行核對的項目由人照清單核對；需要工具的項目由人執行工具，把原始 log 與 hash 記成證據紀錄 | 服務自動執行或派工 |
| 版本同步 | 由人在派工前、放行前用 git diff 與 hash 對照 | 服務自動執行 |
| 正式紀錄與寫入權限 | 由人在受保護的 branch 提交正式紀錄；核准由核准人自己執行簽核指令送出 | 只有服務帳號可寫 |
| 隔離與 CI 規則 | 必須（有禁看 branch 的專案從第一天就要隔離） | 必須 |
| GUI、雙來源監控、遠端執行端、自動派工、3 輪自動停止 | 不需要 | 逐步加上 |

## 1.7 用語表

**流程**

| 用語 | 意思 |
| :---- | :---- |
| 節點 | 流程上的一站。分專案層（P0–P7）、模組層（M1–M7）與變更（C） |
| 階段 | 專案層的節點 P0–P7，每個專案各跑一次 |
| 模組 | 會改到同一塊 code 的一組 CR，例如 lcp、host 介面、安全。由 P2 差異分析切分 |
| 模組流程 | 每個模組各跑一次的 M1–M7 |
| 範圍 CR | 第一次通過 G1 前，在 P0／P2 整理並納入這版範圍的 CR。P0 依它定範圍清單，P2 把它對到 code |
| 變更 CR | 第一次通過 G1 後，不在需求基準裡的 CR 新增或修改，由 C 變更分析處理。以 G1 核准紀錄綁定的快照為準，不看 Jira／Confluence 上是什麼時候改的 |
| 需求基準 | G1 審核通過的來源快照、CR 修訂紀錄與差異分析的確切版本與 hash。第一次通過 G1 後，新增或修改需求都走 C；GC 接受後依影響更新基準，保留原版本與核准歷史 |
| 關卡 | 需要人核准的點：G0–G3、GC、H1、H2，以及 P7 的人確認 |
| 節點卡 | 一個節點的規格，分「介面」（框架固定）與「實作」（可替換）兩段 |
| 執行者 | 實際做一個節點的角色，有四種：AI（skill／agent）、工具（build、ICE、測試框架等結果固定的）、人、串接層自己 |

**產出與紀錄**

| 用語 | 意思 |
| :---- | :---- |
| 產出物 | 每一站交出的檔案（spec、計畫、diff、報告…），有編號、版本與內容 hash |
| 來源快照 | 由工具從 Jira、Confluence 抓下來凍結的需求來源（CR、spec 頁）。AI 只讀快照，不直接拿線上的內容當依據（[03 §3.2](03_artifacts.md#32-編號版本與-hash)） |
| 交接清單 | 每一站結束時交出的固定格式清單：用了哪些上游、交出哪些產出物、有哪些待確認事項或缺口。只是「申請」 |
| 交接包 | 一站交出的產出物加上它的交接清單 |
| 證據紀錄 | 一次檢查留下的紀錄：檢查了哪個版本、用了哪些輸入、結果是什麼 |
| 執行紀錄 | 一個節點的一次嘗試：固定的輸入版本、狀態、log 與結果。一個節點可以有多次嘗試 |
| 正式紀錄 | 只有串接層能寫的紀錄：哪些產出物已通過、核准索引、正式進度、版本同步報告 |
| 已通過／有效／過期 | 產出物的狀態：「已通過」是串接層核對通過；「有效」是它依賴的上游與證據都還是目前的版本；上游改版後變成「過期」 |

**串接層**

| 用語 | 意思 |
| :---- | :---- |
| 串接層 | 負責派工、檢查、放行與退回的確定性流程管理者（不是 LLM）。步驟 2 由人扮演，步驟 3 起由串接層服務擔任 |
| 串接層服務 | 實作串接層的背景程式；GUI、CLI、API 都只是它的入口 |
| 執行端 | 實際執行節點或檢查的機器與程式（AI session、build、測試框架） |
| 檢查 | 出口條件的最小單位，定義在 [05](05_checks.md) |
| R 失敗分類 | 發現問題時，依規則判斷是哪一類失敗、退回哪一站 |
| C 變更分析 | 判斷變更 CR 改到哪個產出物、哪些下游要重做的節點 |
| S 版本同步 | 開啟專案、偵測到新 commit、派工前、放行前都會執行的版本比對與影響檢查；也定期比對來源快照和 Jira／Confluence 的差異（外部來源同步） |
| GLADOS 專案 | 有專案編號的一份需求範圍與流程實例。同一個 FW repo 可以有多個 GLADOS 專案 |
| 專案設定 | 每個專案接上 GLADOS 時要填的設定（[07](07_project_profile.md)） |
