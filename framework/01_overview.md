## 1.1 目標與範圍

**GLADOS 要做到的事**：從需求（spec、CR）出發，經過需求釐清、驗收定義、實作、驗證、整合與全量驗收，最後產出一版功能正常、可以使用的 bootcode FW code。工作由 AI agent／skill、MCP、工具、人分工完成；流程切成多個**節點**，每一站交出產出物與交接說明，擋關的檢查通過才往下走。

**GLADOS 的本意是加速開發**：機制只用來擋住真的會出事的錯（編不過、測試沒過、AI 越界改檔、交錯版本），不用來要求文件長得對不對。

**適用範圍**：Phison 的 bootcode 專案，包括：

- 不同 CPU 與 toolchain（ARM Cortex-R5／DS-5、Andes RISC-V）。
- 新 IC，或從前代 IC 延伸（delta）的專案。
- mask ROM 或非 ROM 的 boot code。

E39（PS5039）是第一個用來開發與驗收 GLADOS 的專案，見 [projects/E39.md](../projects/E39.md)。

**五個設計目標**：

| 目標 | 意思 | 靠什麼達成 |
| :---- | :---- | :---- |
| 可驗證 | 每一站做完都能客觀判斷合不合格 | 擋關的檢查寫成可執行的工具或自動核對；先定驗收再寫 code |
| 可追溯 | 從 code 找得到為了哪條需求、哪個 case | spec 條目與 case 有編號，case 引用 spec 條目；執行與核准紀錄綁 commit |
| 可重入 | 需求變更或失敗時，只重做受影響的部分 | 串接層列出受影響的節點，由人決定從哪裡重做 |
| 可替換 | 任何節點可以換成別的 agent、模型或人來做 | 框架只規定交什麼、怎樣算過；擋關檢查由串接層統一執行 |
| 可累積 | 這次的錯變成下次的能力 | P7 回寫到知識庫、規則、skill、hook |

## 1.2 核心概念

整套框架靠六個概念運作。

1. **節點**：流程切成專案層的 P0、P1、P2、P4–P7，每個模組各跑一次的 M1、M2、M4、M5、M6，以及處理變更 CR 的 C。每個節點有一張節點卡，寫明它吃什麼、交什麼、怎樣算過、由誰做。→ [02 流程](02_workflow.md)、[nodes/](../nodes/README.md)
2. **兩種執行方式**（v0.10）：**AI 的工作一律由人觸發**。P0、P2、M1、C、P7 的全部，以及 M2、M4、M6 的 AI 工作、P1 的移植與移植審查、P5 的安全審查，由人自己開 agent 照 skill 完成，串接層只負責**開工**（準備工作區與工作包）和**收件**（檢查有沒有交齊、跑擋關檢查）；確定性的工具步驟（P1 的起點檢查、機械替換、量基線，M2 的判別能力，M4 的正式 build，M5、P4、P5 的測試執行）由串接層**執行**，人觸發或自動接續。→ [04 §4.2](04_rules.md#42-兩種執行方式)
3. **擋關檢查與證據**：只有錯了會真的出事的檢查才擋關（build、測試、獨立審查、隔離、交付版本），由串接層執行或派工，留下證據紀錄；節點自己說的「通過」不算。人在場的節點另有收件檢查，只看交齊與結構。→ [05 檢查](05_checks.md)
4. **人工關卡**：人只核准真正的決策：範圍（G0）、需求與架構（G1）、每個模組的需求與驗收（H）、變更（GC）、最終交付（G3）；基線有 FAIL 時才請人處置（GB）。→ [02 §2.4](02_workflow.md#24-人工關卡)
5. **串接層**：一個確定性的流程管理者（不是 LLM）。它開工、派工、執行擋關檢查、記錄核准與進度。→ [04 串接層規則](04_rules.md)、[06 串接層服務的要求](06_service.md)
6. **影響提示**：上游改了、失敗了、需求變了，串接層列出可能受影響的節點，由人決定從哪裡重做。只有一條自動規則：image 變了，用舊 image 跑的測試結果不算。→ [04 §4.4](04_rules.md#44-上游改版與重做)

## 1.3 設計原則

| # | 原則 | 意思 | 落在哪裡 |
| :---- | :---- | :---- | :---- |
| 1 | 機器擋真風險 | 只有「機器能便宜驗證、而且錯了會造成損失」的才擋關 | [05 §5.4](05_checks.md#54-擋關檢查) |
| 2 | 人在場只看交齊 | 人和 agent 一起做的節點，人就是品質把關；串接層收件時只確認該交的都在、結構讀得懂，內容由關卡核准 | [05 §5.5](05_checks.md#55-收件檢查) |
| 3 | 關卡只留決策 | 人核准「做什麼、接不接、能不能交付」；中間產出不逐份簽 | [02 §2.4](02_workflow.md#24-人工關卡) |
| 4 | 提示，人決定 | 上游改版、失敗去向、外部來源差異，串接層只負責發現並列出可能受影響的地方 | [04 §4.4](04_rules.md#44-上游改版與重做)–[§4.7](04_rules.md#47-新-commit-與人工修改) |
| 5 | 每個節點自己的工作方式 | 框架只規定每個節點交什麼、怎樣算過、誰做；需要人的節點，中間過程由人和 agent 自己決定 | [04 §4.2](04_rules.md#42-兩種執行方式) |
| 6 | 只認證據 | 擋關檢查以串接層執行或派工留下的證據為準；節點自己寫的「PASS」不算 | [05 §5.1](05_checks.md#51-只認證據) |
| 7 | 球員不兼裁判 | 審查一定由另一個執行者做；實作的 AI 不能改測試或驗收合約 | [04 §4.8](04_rules.md#48-審查放行)、[05 §5.4](05_checks.md#54-擋關檢查) |
| 8 | 迴圈有上限 | 需要重做的 AI 工作最多 3 輪，超過就交給人；上限由 skill 遵守，跨節點的累計由串接層從紀錄算、寫進工作包，超過只提示 | [04 §4.5](04_rules.md#45-失敗處理) |
| 9 | 框架定介面，實作可替換 | Claude Code、Codex、人、script 都能接手任何節點 | §1.4 |

## 1.4 三層：框架、節點實作、專案

| 層 | 內容 | 放在哪裡 | 什麼時候改 |
| :---- | :---- | :---- | :---- |
| **框架** | 流程、節點介面、產出物與紀錄、檢查、串接層規則與服務要求 | `framework/`，以及 `nodes/` 每張卡的「介面」段 | 流程本身要改時才改；對所有專案都一樣 |
| **節點實作** | 誰來執行、用哪個模型與工具、怎麼接 openBCT 或 remote-ice、串接層服務怎麼寫 | `nodes/` 每張卡的「實作」段，以及 `impl/` | 換工具、換模型、補能力時改；不影響框架 |
| **專案** | 專案設定、範圍、試點、專案自己的待決事項 | `projects/` | 每個專案一份 |

三層之間的規則：

1. **框架只規定「要交什麼、怎樣算過、誰做」**，不規定中間怎麼做、用什麼工具做。
2. **節點實作可以替換**：只要交出節點卡要求的產出、通過擋關檢查，串接層的規則就不用改。
3. **實作做不到介面的要求時，登記成驗證缺口**，由人決定補哪種手段。例如 M5 驗證拿不到「測試當時 FPGA 上是哪個 image」的證明，就登記缺口，不能算通過。
4. **專案需要改流程本身，就回頭修框架**，不讓那個專案自己改一套。

## 1.6 建置路線

這一節是 GLADOS 平台本身的開發順序；專案怎麼跑見 [02 流程](02_workflow.md)。

| 步驟 | 做什麼 | 完成的判斷 |
| :---- | :---- | :---- |
| 1a. 框架文件 | 流程、節點卡、產出物與紀錄、檢查、串接層規則寫成文件（v0.8 完成，v0.9 精簡） | 文件審過 |
| 1b. 打底 | 把既有測試項目轉成測試框架 case；不可逆動作用 hook 擋；準備 P0 要用的資料 | 既有測試項目有對應的 case；不可逆動作的 hook 生效 |
| 2. 手動跑一個模組 | 先照專案的完整範圍跑完 P0–P2（經 G0、GB、G1），再挑一個邊界清楚的模組手動跑完 M1–M6。需要人的節點由人開 agent 做；不需要人的節點由人扮演串接層開獨立 session 執行 | 這個模組產出合格交付，交接說明在每一站都夠用 |
| 3. 接上串接層服務 | 背景服務＋操作入口（openBCT GLADOS 分頁）：開工與收件、派工與回收、擋關檢查、影響提示、進度與核准紀錄 | 一個模組能自動派工跑完，人只出現在需要人的節點與關卡 |
| 4. 擴大到整個專案 | 所有模組、P4 整合、P5 全量驗收、C 變更處理 | 完整產出可以量產的整版 FW（E39 的驗收標準見 [projects/E39 E1](../projects/E39.md#e1-e39-的目的與驗收標準)） |
| 5. 第二個專案 | 換一個專案只填新的專案設定 | 不用改流程就能跑，證明平台是通用的 |

**步驟 2 的 P0–P2 為什麼要照完整範圍**：如果只整理試點模組的那幾張 CR，G1 核准之後，其他 CR 全都會變成變更 CR，要一張一張走 GC；P2 定介面時也沒看過其他模組，之後可能要重做。照完整範圍跑，M1 會晚一點開始，但步驟 4 可以直接沿用。

步驟 5 很重要：只在一個專案上跑通，只能證明 GLADOS 適用於那個專案；在第二個專案上「只換專案設定」也跑得通，才證明它是平台。

**各機制從哪一步開始需要**：

| 機制 | 步驟 2（手動跑一個模組） | 步驟 3 起 |
| :---- | :---- | :---- |
| 擋關檢查、判別能力證明、獨立審查 | 必須，這些是品質的核心 | 必須 |
| 串接層 | 由人照節點卡與檢查扮演 | 串接層服務 |
| 擋關檢查的執行 | 需要工具的由人執行工具，留下原始 log | 服務自動執行或派工 |
| 影響提示 | 由人看 git diff 判斷 | 服務列出受影響的節點 |
| 核准紀錄 | 由核准人自己送出，記下核准的人、時間與 commit | 同左，經 openBCT 送出 |
| 隔離與 CI 規則 | 必須（有禁看 branch 的專案從第一天就要隔離） | 必須 |
| GUI、遠端執行端、自動派工 | 不需要 | 逐步加上 |

## 1.7 用語表

**流程**

| 用語 | 意思 |
| :---- | :---- |
| 節點 | 流程上的一站。分專案層（P0、P1、P2、P4–P7）、模組層（M1、M2、M4、M5、M6）與變更（C）。v0.9 起 P3、M3、M7 不再使用 |
| 模組 | 會改到同一塊 code 的一組 CR，例如 lcp、host 介面、安全。由 P2 規劃切分 |
| 模組流程 | 每個模組各跑一次的 M1、M2、M4、M5、M6 |
| 外部互動 | 由人自己開 agent 照 skill 完成的步驟：P0、P2、M1、C、P7 的全部，以及 v0.10 起所有 AI 的工作。串接層只開工與收件；人或 agent 都可以提交 |
| 派工（工具步驟） | 串接層執行的確定性工具步驟（機械替換、build、上機測試等），人觸發或自動接續。v0.10 起串接層不再派工給 AI |
| 範圍 CR | G1 核准前，在 P0／P2 整理並納入這版範圍的 CR |
| 變更 CR | G1 核准後，新增、修改或取消的 CR，由 C 變更與 GC 處理 |
| 關卡 | 需要人核准的點：G0、G1、H、G3、GC，以及基線有 FAIL 時的 GB |
| 程式碼建立設定 | P0 寫在 `profile.json` 的 `recipe` 區塊，說明如何從固定起點建立初始程式碼：採用哪些外部來源、替換或保留哪些檔案、建立哪些 build 設定，以及允許的寫入與移植範圍；後文可簡稱「建立設定」 |
| 基底 | P1 依起點與已核准設定建立的初始程式碼；模組與整合 branch 都從它開出 |
| 節點卡 | 一個節點的規格，分「介面」（框架固定）與「實作」（可替換）兩段 |
| 執行者 | 實際做一個節點的角色：AI（skill／agent）、工具（build、ICE、測試框架等結果固定的）、人、串接層自己 |

**產出與紀錄**

| 用語 | 意思 |
| :---- | :---- |
| 產出物 | 每一站交出的檔案（spec、合約、diff、報告…），版本靠 git |
| 來源快照 | 由工具從 Jira、Confluence 抓下來凍結的需求來源（CR、spec 頁）。AI 寫進產出物的依據要引用快照（[03 §3.2](03_artifacts.md#32-來源快照)） |
| 交接說明 | 每一站結束時交出的說明：交了什麼、還沒解決的問題、給下一站的話 |
| 工作包 | 外部互動的步驟開工時，串接層準備給人與 agent 的說明：工作區在哪、可讀哪些來源、建議的 skill、要交哪些檔案、會做哪些檢查、目前第幾輪、能不能和其他模組平行 |
| 證據紀錄 | 一次擋關檢查留下的紀錄：檢查了哪個 commit、結果是什麼、原始 log 在哪 |
| 執行紀錄 | 一個節點的一次嘗試：輸入 commit、產出 commit、讀了哪些檔案、結果 |

**串接層**

| 用語 | 意思 |
| :---- | :---- |
| 串接層 | 負責開工、派工、擋關檢查與記錄的確定性流程管理者（不是 LLM）。步驟 2 由人扮演，步驟 3 起由串接層服務擔任 |
| 串接層服務 | 實作串接層的背景程式；GUI、CLI、API 都只是它的入口 |
| 執行端 | 實際執行節點或檢查的機器與程式（AI session、build、測試框架） |
| 擋關檢查 | 錯了會真的出事、沒過就不能往下的檢查，定義在 [05 §5.4](05_checks.md#54-擋關檢查) |
| 收件檢查 | 外部互動節點提交時，只看交齊與結構的檢查，定義在 [05 §5.5](05_checks.md#55-收件檢查) |
| 影響提示 | 某個檔案改了，串接層列出讀過它的節點，由人決定重做哪裡 |
| GLADOS 專案 | 有專案編號的一份需求範圍與流程實例。同一個 FW repo 可以有多個 GLADOS 專案 |
| 專案設定 | 每個專案接上 GLADOS 時要填的設定（[07](07_project_profile.md)） |
