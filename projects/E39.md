# E39：用來驗收 GLADOS 的第一個專案

> **這份文件回答**：E39 怎麼套用 GLADOS、怎麼用它來驗收 GLADOS。框架本身見 [framework/](../framework/01_overview.md)。

---

## E1. 為什麼用 E39、驗收什麼

E39（PS5039）目前由團隊用傳統方式開發。讓 GLADOS 在同樣的起點、同樣的需求下再做一次，傳統做法的成果就是現成的對照組。

| 驗收面向 | 要回答的問題 | 怎麼判斷（細節暫緩） |
| :---- | :---- | :---- |
| **正確性** | GLADOS 產出的 FW 功能正常嗎？ | 和傳統版本跑同一套驗收；兩版行為不同時，以 spec 判定誰對；靜態分析、安全審查、記憶體用量 |
| **可行性** | 這套流程跑得通嗎？成本合理嗎？ | 每一站能不能交出合格的交接；迴圈有沒有收斂；人工介入的次數與時間；和傳統做法的效率比較 |

E39 同時也是建置路線（[framework/01 §1.6](../framework/01_overview.md#16-建置路線)）步驟 1–4 的實作場。

## E3. 驗收實驗的設計要點（細節暫緩）

1. **起點與隔離**：GLADOS 用只含起點 commit 的獨立工作區 repo（E2），agent 的 GitLab 權限也只限於它；GLADOS 的產出不推回原 repo，避免傳統團隊看到（雙向隔離）。知識庫也要固定在 G0 核准的環境清單版本，避免 E39 傳統開發的經驗已經寫進知識庫。
   - 目前知識庫是裝到全機共用的位置，同一台機器上有人更新就會跟著變。要真的鎖住，需要每個專案一份 skill 與知識庫路徑（見 [nodes/P0](../nodes/P0.md)）。
2. **範圍與需求基準**：spec 本體已凍結，但 CR 仍在進來。例如 SDKBOOT-2786（PMIC 的 I2C backdoor）10/01 才提出、要求 10 月中前完成。G0 固定這版範圍、起點與環境；第一次通過 G1 前的新 CR 在 P0／P2 整理，改範圍就回 P0 重開 G0。第一次通過 G1 後才走 C 變更分析；要用某張 CR 演練 C，必須在 G1 建立需求基準後引入。
3. **逐張 CR 比較**：傳統做法每張 CR 都有 branch，可以和 GLADOS 的結果逐張比對。GLADOS 在 P2b 做的「修改」（需求內容和原 CR 不同）要記成實驗偏差，比對時標註，因為兩邊做的需求已經不一樣。
4. **人的資訊外洩**：P0b、P2b、M1b 回答問題的人如果參與過傳統 E39 開發，答案要標註來源（「spec／Jira 查得到」或「憑 E39 經驗」）。
5. **效率要分兩本帳**：平台的一次性建置成本，和每張 CR 的邊際成本分開計算。

## E5. E39 CR 盤點與試點模組

Epic `SDKBOOT-2148` 底下的 Change Request 共 **36 張**（2026-10-06 重掃），其中 1 張（2482）是 REJECTED，實際 35 張。

- 狀態：Open 23、In Review 11、Evaluated 1、REJECTED 1。
- 依標題標籤：FIP 10、Security 9（含 2 張 Security／MP）、System 7、MP 4、無標籤 6。
- 10/05 用「標題含 `[PS5039]`」只找到 33 張，漏掉 2422（eFuse 關閉 landmark 寫入）、2528（UART CQ delay 由 eFuse 控制）、2786（PMIC I2C backdoor）。這就是專案設定裡「CR 來源要以 Epic 為準」的由來。
- 完整清單見 Confluence 子頁面第 11 節。

建置路線步驟 2 的試點模組候選（只依標題）：

| 候選 | 理由 |
| :---- | :---- |
| 2421 ID page HMAC check | 好壞情境明確、出錯時會拒絕（fail-closed） |
| 2467 backdoor 寫入範圍限制 | 適合邊界值測試 |
| 2258 burner bin size overflow | 邊界值、好壞情境明確 |

不建議先做：NAND 廠牌相關（2284、2286、2480、2488，FPGA 上不一定有那顆 NAND）、power flow 與 HW bug 類。

## E6. C 變更分析的 E39 例子

ID page HMAC check（2421）已經做到 M5，這時進來一張變更 CR：HMAC key 改用 HW key（類似 2283）。

- C 判斷：改的是「key 來源」那一條 spec → 屬於「改既有模組的需求」。
- GC 核准後：那條 spec 出第 2 版 → 對應的 case、計畫步驟、commit 過期 → 從 M1 重走這條鏈。
- H1 審這一條的差異與受影響範圍；M2 更新對應的驗收合約與 case，合約變更經 H2 核准；M3 確認或更新計畫，M4 依計畫修改 key 載入程式。
- 「簽章正確／錯誤時的行為」等沒受影響的 spec 與 case 定義保持有效，但舊 image 的 PASS 不能證明新 image 是對的。
- image 變了，這個 image 的 M5、P4、P5 驗證證據全部過期並重跑；報告另外綁定目前的測試集合與驗證環境。

## E7. E39 待決事項

1. G0 固定範圍的日期、G1 要採用的需求來源版本；spec 來源要列哪些 Confluence 頁面。知識庫版本仍在 G0 的環境清單固定，不因 G1 前更新需求快照而跟著更新。
2. 模組切分原則；跨兩個 code 模組的 CR 是在 P2b 拆分，還是整張歸其中一個模組。
3. 試點模組選哪一個。
4. burner 的 build 方式。
5. M1b 由誰回答問題（是否找沒參與傳統 E39 開發的人）。
6. Epic 底下約 200 張 sub-task 是不是 E39 的測項清單？如果是，就當作 M2 驗收合約的來源，並在打底時對照現有 openBCT case，找出還沒有 case 的項目。
7. 2786（PMIC I2C backdoor，10/01 提出、要求 10 月中前完成）要不要在 G1 建立需求基準後引入，作為演練 C 變更分析的第一張變更 CR；若 G1 前已納入，就不算這次的變更 CR。
8. E39 的獨立工作區 GitLab project 由誰建立、權限怎麼設；CI 排除規則和 devops 確認（E2）。
9. 知識庫怎麼真的鎖在環境清單的版本（E3 第 1 點）。
10. 各關卡的核准人是誰；M1b、P2b 回答問題的人和核准人是否要分開。
