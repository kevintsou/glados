# bcgen 怎麼接進 GLADOS

> **這份文件回答**：bct_knowledge_base 的 bcgen（公版 bootcode 產生工具）要改成什麼樣子，才能在 P0、P1 讓 AI 使用、參與和人的討論。屬於實作。
>
> **和框架的關係**：bcgen 是節點用的工具，放在實作層；框架不因為它改變。本文件的每一條限制，都是為了守住框架既有的規則（只認證據、可寫範圍、隔離、環境清單）。
>
> **背景評估**：bcgen 現況、在 P0／P1 能做與不能做的事、缺口與驗收條件，見 [assessments/bcgen-p0-p1](../assessments/bcgen-p0-p1/README.md)（2026-10-08，針對 bct_knowledge_base `4582011`）。用 E39 起點實際跑過的結果見同一份評估的 [§13](../assessments/bcgen-p0-p1/README.md#13-補充e39-起點實測2026-10-12)（2026-10-12，針對 `2b6a8cb`）。

## B1. 決策（2026-10-10）

- **bcgen 長出 MCP**，讓 AI 在 P0a 盤點起點、P0b 和人討論、P1 開始時核對使用。原本的網頁精靈與命令列保留，三個入口共用同一套核心程式。
- **MCP 第一版只開唯讀工具**。會寫東西的功能（產生專案、帶入 HAL、新增功能、存設定）不開給 P0／P1 的節點。
- **新 IC 的起點在 P0 之前、流程外準備**：用 bcgen 產生骨架、補到能跑、提交成一個 commit，再交給 P0 選用（B7）。E39 是 delta 專案，起點是現成的 code，用不到產生功能。
- **框架不變**：bcgen 是 P0、P1 實作段的工具；盤點結果是工具輸出，P0 的正式產出仍是專案說明、範圍清單、專案設定、環境清單四份。
- **實作順序（2026-10-12）**：建置路線步驟 2 先用固定輸入的唯讀 JSON CLI，補好 ARM 起點盤點與 P0／P1 欄位對應；MCP 留到步驟 3 接上串接層服務時再做（B8）。CLI 不依賴 MCP 或服務才能執行。

## B3. 守住的規則

| # | 規則 | 為什麼 | 依據 |
| :---- | :---- | :---- | :---- |
| 1 | **MCP 只給唯讀工具**。產生專案、帶入 HAL、新增功能（會寫進共用的功能清單）、存設定，都不開給 P0／P1 的節點；節點設定用 MCP 白名單擋住 | P0、P1 都不能改 FW code，也不能改共用的知識庫 | [nodes/P0](../nodes/P0.md)、[nodes/P1](../nodes/P1.md) 的可寫範圍 |
| 2 | **AI 自行透過 CLI 或 MCP 查到的結果只供參考**，不能當放行依據。要當證據時，由串接層以固定輸入獨立執行 CLI，留下原始報告、hash 與證據紀錄；步驟 2 由人扮演串接層執行，步驟 3 改由服務派工 | 只認證據：節點自己跑的結果只供參考；手動階段也要遵守相同的證據規則 | [framework/05 §5.1–5.2](../framework/05_checks.md#51-只認證據)、[framework/01 §1.6](../framework/01_overview.md#16-建置路線) |
| 3 | **每次都綁定固定的輸入**：一開始指定起點 repo 與 commit（以及功能清單、過往問題清單、公版 code 包的版本），之後每個回應都附上來源位置與 hash。不讀 `settings.json` 的路徑，也不掃指定範圍以外的目錄 | 證據要對應目前版本；有隔離限制的專案（E39）不能讓 AI 透過工具讀到禁看的內容 | [framework/03 §3.12](../framework/03_artifacts.md#312-存放位置與寫入權限)、[projects/E39](../projects/E39.md) |
| 4 | **回應分清楚「讀到」「推測」「不知道」**，三種分開列；「沒找到」不能寫成「沒有」 | P0b 討論時，人要知道哪些是事實、哪些要自己確認 | — |
| 5 | **保存草稿與核准分開**：P0a 可依可寫範圍保存四份 P0 產出的候選草稿，不需每次寫檔都等人確認；P0b 由人確認範圍與設定決定，G0 再核准四份產出的確切版本。bcgen CLI／MCP 的唯讀介面只回傳候選資料，不代寫 P0 產出或存 bcgen 設定；人與 AI 的並行操作要避免互相覆蓋 | P0a 無人在旁，必須能交出草稿；保存檔案不代表定案或核准 | [nodes/P0](../nodes/P0.md) 的可寫範圍與 G0 |
| 6 | **版本依用途鎖定與分類**：CLI／MCP 回報 bcgen 程式、功能清單、過往問題清單、公版 code 包各自的版本與 hash，列進環境清單。AI 查詢與草擬用途屬於「只影響 AI」；串接層派工、會影響正式檢查判定的 checker／adapter 與規則屬於「影響驗證」；用來產生起點的工具與輸入屬於「影響 build」。同一項有多種用途時分別記錄角色與相依版本 | 環境就緒要核對實際版本；查詢用途改版不讓已通過的產出物過期，驗證用途改版讓使用舊 checker／規則的相關報告過期並重跑，影響判定方式時依既有規則評估重開 H2；build 用途改版依框架讓所有證據過期 | [framework/04 §4.4](../framework/04_rules.md#44-過期與重新進入) |

另外：

- **不破壞 bcgen 只靠標準函式庫的特性**：MCP 需要的套件只在啟動 MCP 時才載入；沒裝的機器照樣能開網頁精靈與命令列（和 openBCT `AGENTS.md` 的做法一樣）。
- **工具要誠實回報自己的能力**：支援哪些 CPU、平台、image 組合，哪些檢查真的有實作（例如過往問題清單規劃了 12 個自動檢查，目前只實作 1 個），都要能查到，避免 AI 誇大工具做得到的事。

## B4. MCP 工具（第一版，全部唯讀）

| 工具 | 做什麼 | 用在哪一站 |
| :---- | :---- | :---- |
| `open_context` | 指定起點 repo、commit 與各項資料的版本，固定這次的輸入，回傳 context 編號與各輸入的 hash | P0a、P1 |
| `inspect_start` | 盤點起點：CPU、系列、build target、記憶體區域、eFuse、register、功能線索；每項附來源與「讀到／推測／不知道」 | P0a |
| `check_config` | 用 bcgen 現有的檢查規則，找出設定（或專案設定草稿）裡的錯誤與警告，附檢查代號 | P0a、P0b |
| `feature_dependencies` | 查功能相依，例如「移除 A 會影響哪些功能」 | P0b |
| `find_references` | 某個函式在起點 code 裡怎麼寫、誰呼叫；只查 context 指定的範圍 | P0b |
| `applicable_pitfalls` | 依 CPU、系列、功能，列出適用的過往問題，以及每條檢查是自動（已實作／規劃中）或人工 | P0b |
| `capabilities` | 列出支援的 CPU、平台、image 組合，以及實際有實作的檢查 | 所有用到 bcgen 的節點 |
| `profile_draft` | 把盤點結果轉成 [framework/07](../framework/07_project_profile.md) 專案設定的欄位草稿，並列出缺哪些欄位 | P0a |
| `check_build_targets` | 核對起點盤點出的每個 target 是否已在專案設定處置為必要或明確排除（B5；對應 BLD-001「只編了自己的 target」）；實際 build 證據仍由串接層的 build 檢查核對 | P0 出口、P1 開始時 |
| `version` | 回報 bcgen 程式、功能清單、過往問題清單、公版 code 包的版本與 hash | P0 環境就緒、任何節點 |

每個回應都帶：context 編號、輸入的版本與 hash、每一項的來源（檔案、行號、檔案 hash）與觀察程度（讀到／推測／不知道）。

**不開放的功能**：產生專案（`generate`）、帶入 HAL（掃描後套用、自動帶入）、新增功能（寫 `features_custom.json`）、存設定（`settings.json`）。之後要給「準備新 IC 起點」用時，另外做一組，不放進 P0／P1 節點的 MCP 白名單。

**用 E39 起點實測後的限制**（評估 [§13](../assessments/bcgen-p0-p1/README.md#13-補充e39-起點實測2026-10-12)）：

- `inspect_start`：CPU、記憶體區域、eFuse、帶入 code 的來源位置讀得到。ARM 起點的系列、image、build 設定目前會漏掉或給預設值，補上 ARM 起點的匯入（B8 第 1 階段）之前，這三項一律標成「不知道」。功能清單只勾得到 1 個，E39 的既有功能要從其他來源盤點（[nodes/P0](../nodes/P0.md) 的待展開議題）。
- `check_config`：要分「盤點」與「產生」兩種模式。盤點既有起點時，產生 code 才需要的欄位（例如 UART 參考時脈、`EFUSE_BANK_COUNT`）不報 error。
- `check_build_targets`：DS-5 起點的 build 設定寫在 `.cproject`，要先能讀它才做得出來。

## B5. 在 P0、P1 怎麼用

下面以 B4 的核心操作名稱描述流程；建置路線步驟 2 透過唯讀 JSON CLI 使用，步驟 3 再提供同名 MCP 入口，兩者共用固定輸入與能力限制。

**P0a 草擬**（AI，無人在旁）

1. `open_context`：指定只含允許 branch 的工作區 repo 與起點 commit。
2. `inspect_start`、`profile_draft`、`check_config`：取得起點的盤點與專案設定草稿。
3. 草擬範圍清單時，把盤點到的既有功能列成候選，來源欄引用 bcgen 回報的 code 位置；「推測」與「不知道」的項目列成要問人的問題，交給 P0b。
4. 依 P0 的可寫範圍，保存專案說明、範圍清單、專案設定、環境清單四份候選草稿；bcgen 回應本身仍是工具輸出。

**P0b 討論**（人＋AI）

- AI 在討論中用 `feature_dependencies`、`find_references`、`applicable_pitfalls` 回答問題，例如「這個功能拿掉會不會影響別的」「起點 code 這段怎麼寫」「這類功能過去踩過什麼坑」。
- 人可以同時開網頁精靈看記憶體與 eFuse 的畫面；AI 可更新 P0 候選草稿，人確認討論中的決定後送 G0 核准確切版本（B3 第 5 條）。

**P0 出口與環境清單**

- P0 的出口檢查不因 bcgen 而改變。要拿 bcgen 的檢查結果當證據時，由串接層用命令列執行（B3 第 2 條）。
- 環境清單列 bcgen 的各項版本與類別（B3 第 6 條）；「環境就緒」用 `version` 核對。
- 起點盤點出的 target 都要在專案設定既有的「build 設定」欄位中處置：列為**必要**，或**明確排除並附理由與範圍依據**。P0a 可先標成待確認，P0b 必須解決後才送 G0；沒找到或不支援的盤點結果不能當成清單已完整（[framework/07 §7.2](../framework/07_project_profile.md#72-填寫規則)）。
- 盤點到 target 不代表這一版一定要 build；排除也不代表它 PASS。排除理由不能只是 build 失敗、工具不支援或為了讓基線通過；不得排除專案範圍所需的設定。G0 核准必要清單與排除理由。

**P1 基線建立**

- `check_build_targets`：以固定的起點重新核對盤點清單和 G0 核准的必要／排除處置。漏列、仍待確認、必要設定不存在於起點，或無法完整盤點時，P1 回報「輸入不足」，由 R 退回 P0（[framework/04 §4.5](../framework/04_rules.md#45-r-失敗分類)）。核准的排除項目不要求 build，也不計入 PASS。
- P1 出口由串接層核對 G0 核准的每個必要設定都有實際 build 成功、0 warning、image hash 的證據。target 盤點或 checker 的 `ok` 不能取代 build 結果；必要設定 build 失敗時依 P1 的失敗規則交給人，不能在 P1 自行改成排除。
- P1 的基線仍由原本的 build 與測試建立；bcgen 不產生、不修改起點，它的結果也不能取代 build 與測試的證據。

## B7. 新 IC 的起點準備（流程外）

新 IC 用 bcgen 的公版骨架當起點時，骨架大多還是空殼，P1 跑不過；但 P0、P1 都不能改 FW code。所以起點在 P0 之前、流程外準備：

1. 用 bcgen 產生骨架，補必要的平台 hook 與 HAL，補到起點必備的最小能力能跑（例如初始化完成、UART 輸出指定訊號）。
2. 封存產生時的輸入（專案設定 JSON、bcgen 與公版 code 包的版本與 hash、register header）與輸出檔案清單。
3. 提交成一個 commit。G0 核准的是這個 commit，不是 bcgen 的暫存輸出目錄。
4. 之後照一般 FW 流程維護 source；不在 P1 或之後的節點重新執行 bcgen 產生（它每次會清空輸出目錄）。

這個準備工作目前不由 GLADOS 管理。等第一個用 bcgen 起點的新 IC 專案出現，再決定要不要把「起點準備」變成正式的一站（B9 第 4 項）。

## B8. 改 bcgen 的順序與驗收

| 階段 | 做什麼 | 驗收 |
| :---- | :---- | :---- |
| 1. 固定輸入與命令列 JSON | 每次執行明確指定起點 repo、commit 與資料版本；掃描只限指定範圍；`check` 與盤點輸出 JSON（附來源、hash、讀到／推測／不知道）；`version` 回報各項版本與 hash。ARM 起點的匯入：讀 DS-5 `.cproject` 的 build 設定、認得 `burner.scat`、判斷系列；`check` 分盤點與產生兩種模式（B4 末段） | 同樣的輸入得到同樣的結果；不寫入任何檔案；指定範圍以外的路徑會被拒絕；不支援的組合明確回報；E39 起點（`83dc1a65b`）盤點出系列 duan、image boot＋sandaru、`.cproject` 的 6 個 build 設定；盤點模式不因產生用的欄位報 error |
| 2. P0／P1 的 CLI 對接（建置路線步驟 2） | `profile_draft` 對應 GLADOS 專案設定欄位；`check_build_targets` 區分盤點與必要／排除處置；由人扮演串接層獨立執行 CLI 留證據 | 不需 MCP 或服務即可使用；草稿沒有機器路徑，缺的欄位有列出；漏列或待確認會擋住交接，核准且有理由的排除不算遺漏也不算 PASS；必要設定全部要求實際 0 warning build 證據 |
| 3. MCP 與服務對接（建置路線步驟 3） | 在同一套核心上提供 B4 的唯讀工具；MCP 套件延遲載入；節點設定 MCP 白名單，服務獨立派工 CLI checker | 工具清單沒有任何寫入功能；每個回應帶 context 與來源；沒裝 MCP 套件時網頁精靈與 CLI 照常運作；AI 查詢與正式檢查的執行紀錄可區分 |

評估文件第 7 節列的缺口（build 腳本不回傳 make 失敗、輸出目錄會被清空等）屬於產生功能，在 B7 的起點準備用到時再修。

## B9. 待決事項

1. 誰來改 bcgen，改動走 bct_knowledge_base 的哪個審查流程。
2. MCP 用官方 `mcp` 套件（要另外安裝），還是用標準函式庫自己實作 stdio 協定（維持零相依）。
3. 盤點報告要不要成為 P0 的正式附件。目前只當工具輸出；要變成正式產出物，就是改框架。
4. 「起點準備」要不要變成正式的一站（等第一個用 bcgen 起點的新 IC 專案）。
