# bcgen 怎麼接進 GLADOS

> **這份文件回答**：bct_knowledge_base 的 bcgen（公版 bootcode 產生工具）在 GLADOS 裡用在哪裡、要改成什麼樣子。2026-10-19 起只用在 P1 的機械替換，由串接層執行；P0 不經 bcgen 盤點。屬於實作。
>
> **和框架的關係**：bcgen 是節點用的工具，放在實作層。接進 GLADOS 時發現起點盤點出的 build 設定要逐項處置（E39 的 `.cproject` 有 6 個，專案設定原本只列 4 個），這一點改在框架（v0.8.1：[framework/07 §7.2](../framework/07_project_profile.md#72-填寫規則)、[framework/05 §5.5](../framework/05_checks.md#55-各節點的檢查)），對所有專案都適用。本文件其他每一條限制，都是為了守住框架既有的規則（只認證據、可寫範圍、隔離、環境清單）。
>
> **背景評估**：bcgen 現況、在 P0／P1 能做與不能做的事、缺口與驗收條件，見 [assessments/bcgen-p0-p1](../assessments/bcgen-p0-p1/README.md)（2026-10-08，針對 bct_knowledge_base `4582011`）。用 E39 起點實際跑過的結果見同一份評估的 [§13](../assessments/bcgen-p0-p1/README.md#13-補充e39-起點實測2026-10-12)（2026-10-12，針對 `2b6a8cb`）。評估是針對原本「P0 用 bcgen 盤點」的設計寫的，2026-10-19 後只當歷史參考。

## B1. 決策

- **（2026-10-19，依使用者決定）P0 不經 bcgen；bcgen 只用在 P1 的機械替換**：P0 由 AI 直接讀指定起點 commit 的 build 設定、feature 條件與 code 引用來盤點（[nodes/P0](../nodes/P0.md)，實作是 bct-p0 skill）；bcgen 專注依生成配方產出 code base。原本規劃給 AI 與串接層用的唯讀 JSON 命令列（`inspect_start`、`profile_draft`、`check_build_targets` 等）不做，各項工作的去處見 B4。E39 實測時 bcgen 的功能清單只勾得到 1 個功能，既有功能本來就要從起點 code 與其他來源盤點（評估 [§13](../assessments/bcgen-p0-p1/README.md#13-補充e39-起點實測2026-10-12)）。
- **（2026-10-13）bcgen 不做 MCP**：MCP server 通常全機註冊、只指向一個版本，和每個專案固定工具版本的要求衝突。10-19 起連給 AI 用的命令列也不做，這一條只留作紀錄。
- **AI 不呼叫 bcgen**。P0／P1 AI 節點的命令允許清單不列 bcgen；會寫東西的功能（產生專案、帶入 HAL、新增功能、存設定）只由人（網頁精靈）或串接層（P1 機械替換）使用。
- **（v0.8.5 修訂）新專案的 code base 在 P1 建立**：P0 討論定案的生成配方就是 bcgen 的輸入；P1 由串接層執行 bcgen 或 script 做機械替換（例如換上新 IC 的 register、建立 IC 目錄與 build 設定），做不到的部分由 AI 在限定的移植範圍內補足，經獨立審查與 GB 核准（[nodes/P1](../nodes/P1.md)）。E39 也是這樣：以 PS5037 的 code base 為起點，換上 PS5039 的 register。bcgen 的生成功能要支援「以前代 code base 衍生」與 ARM，才能用在 E39；順序與驗收見 B8。B7 的「流程外準備」只剩全新骨架、還沒有任何可 build 起點的情況。
- **（2026-10-19，依使用者決定）配方就是 bcgen 的輸入**：P0 定生成配方時，直接把起點、外部來源、register block 對照、生成區、起始複製區、移植範圍、build 設定對應寫進專案設定的配方區塊，不留到 P1 才收資料，也不另存 bcgen 專用檔。配方的機器格式由 GLADOS 定義（[impl/recipe](recipe.md)），bcgen 的衍生模式照這個格式嚴格讀取（BC-008）；bcgen 現有給公版骨架用的 `projects/<ic>.json` 不用在這裡。
- **bcgen 對框架的影響**：沒有。P0 的正式產出仍是專案說明、範圍清單、專案設定、環境清單四份；「每個 build 設定都要處置」的規則（v0.8.1）不變，只是正式檢查改由串接層的確定性 checker 執行（B5）。

## B3. 守住的規則

| # | 規則 | 為什麼 | 依據 |
| :---- | :---- | :---- | :---- |
| 1 | **AI 不呼叫 bcgen**：P0／P1 AI 節點的命令允許清單不列 bcgen；P1 的機械替換由串接層執行，移植的 AI 只改移植範圍 | P0、P1 的 AI 都不能改 FW code（移植範圍除外），也不能改共用的知識庫；機械替換要可重現，不能由 AI 臨場決定 | [nodes/P0](../nodes/P0.md)、[nodes/P1](../nodes/P1.md) 的可寫範圍 |
| 2 | **只認串接層執行的結果**：機械替換的輸入、輸出清單與 hash 由串接層記錄，當作基底建立紀錄的證據；人或 AI 自己跑的結果只供參考 | 只認證據：節點自己跑的結果只供參考 | [framework/05 §5.1–5.2](../framework/05_checks.md#51-只認證據) |
| 3 | **每次都綁定固定的輸入**：版本由串接層固定——依 G0 核准的設定與環境清單準備起點 worktree 與快照，把位置明確傳給 bcgen，正式 hash 由串接層自己計算（OBC-031）。bcgen 只讀傳入的輸入：不讀 `settings.json`、全域 catalog、環境變數或快取，不掃傳入範圍以外的目錄（BC-001）；回報讀到的檔案與 hash，供串接層核對 | 證據要對應目前版本；有隔離限制的專案（E39）不能讓工具讀到禁看的內容 | [framework/03 §3.12](../framework/03_artifacts.md#312-存放位置與寫入權限)、[projects/E39](../projects/E39.md) |
| 4 | **版本依用途鎖定**：環境清單列 bcgen 程式、功能清單、公版 code 包與生成配方輸入的固定版本與 hash；用來產生基底的工具與輸入屬於「影響 build」 | 換版會讓基底與所有證據過期，屬於改基底 | [framework/04 §4.4](../framework/04_rules.md#44-過期與重新進入) |

另外：

- **不破壞 bcgen 只靠標準函式庫的特性**：命令列只用 Python 標準函式庫，不需要另外安裝套件。
- **工具要誠實回報自己的能力**：不支援的 CPU、平台、image 組合，或生成配方有缺項、對照不到時，要明確失敗並列出缺什麼，不能產出一份看起來完整、實際不能用的 code base。

## B5. 在 P0、P1 怎麼用

**P0**

- 不用 bcgen 盤點或查詢。AI 直接讀起點 code（[nodes/P0](../nodes/P0.md)）。
- 定生成配方時直接寫進專案設定的配方區塊（B1、[impl/recipe](recipe.md)）；環境清單列 P1 要用的 bcgen 版本與它支援的配方格式版本（B3 第 4 條）。
- 起點盤點出的 target 都要在專案設定既有的「build 設定」欄位中處置：列為**必要**，或**明確排除並附理由與範圍依據**。P0a 可先標成待確認，P0b 必須解決後才送 G0；沒找到或不支援的盤點結果不能當成清單已完整（[framework/07 §7.2](../framework/07_project_profile.md#72-填寫規則)）。
- 盤點到 target 不代表這一版一定要 build；排除也不代表它 PASS。排除理由不能只是 build 失敗、工具不支援或為了讓基線通過；不得排除專案範圍所需的設定。G0 核准必要清單與排除理由。
- 「每個 target 都已處置」的正式檢查，由串接層的確定性 checker 獨立列舉固定起點的 build 設定、比對專案設定（OBC-030）；AI 自己盤點的結果只供參考。

**P1 基底與基線建立**

- 開始時，用同一個 checker 以固定的起點重新核對盤點清單和 G0 核准的必要／排除處置。漏列、仍待確認、必要設定不存在於起點，或無法完整盤點時，P1 回報「輸入不足」，由 R 退回 P0（[framework/04 §4.5](../framework/04_rules.md#45-r-失敗分類)）。核准的排除項目不要求 build，也不計入 PASS。
- 機械替換由串接層依生成配方執行 bcgen，輸入固定、只寫生成區與起始複製區、重跑結果相同（OBC-031、BC-007、BC-008）。
- P1 出口由串接層核對 G0 核准的每個必要設定都有實際 build 成功、0 warning、image hash 的證據。target 盤點或 checker 的 `ok` 不能取代 build 結果；必要設定 build 失敗時依 P1 的失敗規則交給人，不能在 P1 自行改成排除。
- P1 的基線由實際的 build 與測試建立，bcgen 的產出不能取代 build 與測試的證據。

| :---- | :---- | :---- |

| P7 回寫 | 過往問題清單、功能清單 | 這次踩到的新坑寫成新的過往問題條目，經人確認；改了就升級環境清單版本 |

## B7. 新 IC 的起點準備（流程外）

> **v0.8.5 起適用範圍縮小**：有可 build 的前代 code base 時（包括 E39），新專案的 code base 改在 P1 依生成配方建立（B1），不走這一節。這一節只適用於完全從公版骨架開始、連起點都還 build 不過的情況。

新 IC 用 bcgen 的公版骨架當起點時，骨架大多還是空殼，P1 跑不過；P1 要求起點至少能 build。所以這種起點在 P0 之前、流程外準備：

1. 用 bcgen 產生骨架，補必要的平台 hook 與 HAL，補到起點必備的最小能力能跑（例如初始化完成、UART 輸出指定訊號）。
2. 封存產生時的輸入（專案設定 JSON、bcgen 與公版 code 包的版本與 hash、register header）與輸出檔案清單。
3. 提交成一個 commit。G0 核准的是這個 commit，不是 bcgen 的暫存輸出目錄。
4. 之後照一般 FW 流程維護 source；不在之後的節點對這份 source 重新執行 bcgen 的整包產生（它每次會清空輸出目錄）。P1 的機械替換是另一種用法，只寫生成區與起始複製區。

這個準備工作目前不由 GLADOS 管理。等第一個用 bcgen 起點的新 IC 專案出現，再決定要不要把「起點準備」變成正式的一站（B9 第 4 項）。

## B8. 改 bcgen 的順序與驗收

（2026-10-19 依「bcgen 只用在 P1」改寫）bcgen 只剩 **B 機械替換**一條線；原本的 A 唯讀盤點線除了 A1 以外都不做。固定版本、準備起點 worktree 與快照、計算正式 hash 都是串接層的工作（OBC-031，[framework/04 §4.2](../framework/04_rules.md#42-派工與放行)）；bcgen 只負責「能被固定」：只讀傳入的輸入。每個階段對應[共用待辦](../docs/coordination/glados-openbct-todo.md)的任務，完成條件以任務檔為準，這裡只列順序與要點。

**A. 原本的唯讀盤點線**

| 階段 | 狀態 | 任務 |
| :---- | :---- | :---- |
| A1. 只讀傳入的輸入 | 完成（bct_knowledge_base `1c97546`）；B 線的共同基礎 | BC-001 |
| A2. 唯讀 JSON 命令列 | 不做（2026-10-19） | BC-002 |
| A3. `check` 分盤點／產生兩種模式 | 不做（2026-10-19）；P0 不用盤點模式，產生模式的檢查歸 B2 | BC-003 |
| A4. P0／P1 對接（`profile_draft`、`check_build_targets`） | 不做（2026-10-19）；target 處置核對改由串接層 checker（OBC-030） | BC-004 |
| A5. E39 資料覆蓋 | 待重新評估：原本是給 P0 盤點用，P0 不用 bcgen 後，只剩生成需要的功能清單資料 | BC-006 |
| A6. 服務對接 | 不做（2026-10-19）；固定輸入與 P1 派工改由 OBC-031 | OBC-011 |

**B. 機械替換（P1 建立基底，v0.8.5 起）**

| 階段 | 做什麼 | 驗收 | 任務 |
| :---- | :---- | :---- | :---- |
| B1. 產生功能的安全性 | make 失敗要回傳失敗；先寫到暫存區，完成後才發布，只寫生成區與起始複製區、不清空這兩區以外的檔案、拒絕覆蓋已凍結的輸出；輸出逐檔清單；stub 與缺檔要分得出「只能當設定檔看」和「可以建立基線」 | 故意讓 make 失敗而 tee 成功，仍回傳失敗；同一份生成配方、工具版本與輸入重跑，產出逐檔相同（[framework/05](../framework/05_checks.md)「機械替換可重現」） | BC-007 |
| B2. 以前代 code base 衍生（含 ARM） | 依生成配方換 register header；以前代 IC 目錄為底建立新 IC 目錄；產生新 IC 的 DS-5 `.cproject` 設定、依記憶體配置更新 scatter；在共用層的 IC 旗標（例如 duan 的 `IC_NAME`）加入新 IC。只做查表就能確定的替換，需要判斷的留給 P1 的移植 | 配方缺項或對照不到時明確失敗並列出缺什麼；用 E39 起點 `83dc1a65b` 加 PS5039 register 快照實際跑一次，產出能交給 P1 的移植步驟 | BC-008 |

**C. 串接層對接**

| 階段 | 做什麼 | 驗收 | 任務 |
| :---- | :---- | :---- | :---- |
| C1. target 處置核對 | 確定性地列舉固定起點的 build 設定（ARM `.cproject`、Andes build 設定），比對專案設定的必要／排除處置；不依賴 bcgen | 漏列、待確認、排除沒有理由、必要設定不存在於起點、起點格式不支援，都明確報出、不算 PASS；P0 出口與 P1 開始用同一個 checker | OBC-030 |
| C2. P1 機械替換派工 | 依 G0 核准的專案設定與環境清單固定 bcgen 與全部輸入，準備 worktree 與快照，執行產生模式，記錄輸入與輸出的 hash | 串接層自己算的 hash 和 bcgen 回報不一致就不放行；同一份輸入重跑逐檔相同；AI 呼叫不到 | OBC-031 |
